## 真实响应的关键差异

### 内容、思考与工具没有标准分栏

5 个流式样本的有用内容均在 `choices[].delta.content`；非流式在 `choices[].message.content`。均未收到标准 `reasoning_content`、`tool_calls` 或结构化工具结果，也没有 `usage`。非流式带 `message.role`，不能将它误记成 delta。

可见标记包括 `<think>`、`</think>`、`## Thought:`、`## Python:`、`## Answer:`、`Worked for …`、`**Used … skill**`、`**Searched 4 websites**`。这些都是正文字符串，不能当成 OpenAI 标准工具协议。

`## Answer:` 也会标记中间进展，并非唯一最终回答边界。混合样本有 4 次 Answer，生图样本的图片还位于第一次 Answer 前。只取第一次 Answer 后内容会混入过程，只取最后一次又可能丢图片与有用进展。

本次有 think 的 5 个样本标签均闭合，但样本 03 的 ` ```python ` 没有结束围栏，后面直接出现 `</think>` 和 `## Answer:`。样本 02 的命令片段以 `data && python …` 开始，缺乏完整的结构化命令参数和独立执行输出。因此不能保证展示的代码完整，也不能把这些片段直接作为本地可执行工具调用。

### 搜索与引用

样本 02 有 `Searched 4 websites` 摘要，但没有实际查询字符串、4 个搜索结果对象或调用 ID。最终回答主要使用普通 Markdown 来源链接，部分含 `utm_source=chatgpt.com`，同一地址可能又以来源括号重复出现。

可复用现有 Markdown/来源展示，并在渠道层对确定的来源做规范化、去重；不能从“搜索了 4 个网站”推导 4 次可计费搜索，也不能补造查询词。下载链接、图片链接、来源链接必须分别识别。

### 生成图片和文件

观测到两种地址形态：

```text
https://files.chat01.ai/user-<opaque>/<image>.png
https://files.chat01.ai/python-generations/<opaque>/<filename>
```

下载不需要 API Authorization。本次生成图片返回 `image/png`；Python 产物（包括 PNG）多返回 `application/octet-stream`，不能只看 Content-Type 就拒绝可预览图片或信任文件类型，应复用现有文件检测。

混合样本同时给出原生生图 CDN 地址、复制到代码环境后的 PNG 和包含该 PNG 的 ZIP。文件身份不能只按文件名去重；同一内容不同 URL 是否复用，应走已下载内容及用户权限下的现有去重规则。

图像生成没有独立的 image_generation 调用对象或可靠 revised_prompt 字段，不能将用户需求自动冒称为工具实际提示词。

### 交互组件确实可能泄漏私有格式

五子棋返回了可复用现有 Artifact 的 html 围栏，另有独立 HTML 文件。这证明可拿到交互源码，不等于拿到了官网的结构化 UI 协议，也不意味着应用当前会自动打开它。

地图样本则包含以下形态的原始字符串：

```text
genui{"map_widget_v2":{"points":[{"ref":"turn…business1"}],"carousel":{"cards":{"turn…business1":{"title":"…","label":"…"}}},"title":"…"}}
```

完整响应中没有与这些 business ref 配套的经纬度或地点数据表，不能直接还原地图。实景图部分出现了图片说明和照片来源网页链接，但没有 Markdown 图片地址或图片数组，不能认定图像本体也传到了 API。

建议隔离识别已知私有标记：有足够数据才转换成项目组件；缺数据时保留有用名称、普通链接和表格，并明确保留该组件的可见入口/缺失状态及原始数据，不无声删除。不为不存在的坐标或图片补造数据。用户明确 HTML 代码块不等于官网交互组件；未取得完整官网组件协议时不开展通用组件仿制。

### 心跳、结束与标识

- 5 次流式共见 52 个空字符串 content 事件。混合任务持续约 3 分 32 秒，事件间最大观测间隔约 15 秒。空内容仍是有效连接活动，不应显示为空消息或当成完成。
- 各流式 chunk 的 `id` 会变化；样本 03 有 130 个 JSON chunk 和 130 个不同 ID。应按本地请求/run 归属管理，不把每个 id 当作新对话或新工具调用。
- `created` 为约 13 位的毫秒值，不能按标准秒值直接格式化。
- 非流式响应头是 `application/json`，正文以三个换行开头，之后才是完整 JSON。请求仍可能保持传输活动，不能把“已有响应头/首个字节”当作完成。
- 当前 DEEIX 上游默认首字节等待 120 秒、流式空闲 60 秒，来自 `backend/internal/infra/llm/client.go`；渠道可覆盖。底层读到心跳字节应续活，不能只以可见文字续活。向浏览器的生成流另有 20 秒 keepalive（`handler_message_send.go`）。
- 未调用 Pro、未测试 40–60 分钟场景、未复现最终一次性思考输出。不能据本次短请求宣称 Pro 全链路已通过；总运行时长、上游空闲、浏览器连接、反代超时需分别验证。

## 后续实现边界

1. **独立 Chat01 渠道适配器**：沿用既有 OpenAI 传输，增加有界增量内容解码；按请求生成稳定内部标识。保留原始诊断，处理分片标记、重复 Answer、EOF 未闭合和代码围栏不完整；不在通用 OpenAI parser 上全局增加文本猜测。
2. **正文、思考、执行过程分别规范化**：最终对接现有 `GenerateOutput`、`ReasoningOutput`、只读工具 trace 与图片/文件结构。过程证据不足的内容以执行记录展示，不虚构参数、stdout、exit code、成功状态或工具调用计费次数，更不能把服务端已执行片段发给本地工具再执行。
3. **图片和文件复用统一产物链路**：现有 `OpenGeneratedFile` 只读 OpenAI 容器，`saveAssistantGeneratedFiles` 只改写 sandbox 链接，不能直接用 CDN URL 替换容器 ID。需在来源适配边界增加 Chat01 文件读取，复用用户权限、存储政策、类型检查与卡片。
4. **单文件失败与回答成功分开**：建议成功文件正常保存、失败文件记录可见状态并保留可尝试的原链接，不让一个 CDN 文件失败清空整段正文或其他已成功文件。当前生成文件保存采用整批回滚，实施时需明确新增的逐文件结果边界；不能仅靠前端换链接假装已保存。外链模式与本地保存模式仍需产品确认。
5. **引用、Artifact 与私有块**：标准链接、表格和 html 围栏尽量复用现有组件；私有 genui 只做已验证转换，缺失数据不硬转。HTML 文件仍走隔离预览，不同源执行。
6. **计费**：本批没有 token usage，调用单价依据用户提供。不能将 Chat01 的摘要文字套用 OpenAI 原生工具价格；额度、身份、成功与失败计量需要渠道自己的明确规则。

- 请求后约 2.1 秒，本地记录到一次额外的 GET 200，User-Agent 为 `got`；最终回答于约 30.5 秒结束，API HTTP 200 与 `[DONE]` 均收到。

- 测试结束已停止两个本地读取服务及 SSH 隧道，移除临时取件凭证文件、TLS 私钥；再次访问隧道返回 502，不能继续读取样件。原始 API 密钥未写入抓包或源码。

本次按用户报价增加 2 分；累计 12 次模型请求、11 次 HTTP 200，成功请求按单价计 20 分，全部请求保守预留 22 分（其中一次既往 400 的实际扣费未知）。未调用 Pro，无付费请求自动重试。

结论：Chat01 不限于读取自家 CDN，这次可以通过短期签名 HTTPS URL 获取本机原件。此结果不证明所有大文件、长任务、Range 行为、部署反代或生产权限链已经通过。私有证据在 `.cache/chat01-probes/20261105/https-proof/` 的 `result.json`、`client-result.json`、`cleanup-result.json` 与 `response.sse`；公开文档不保存可用凭证。生产授权服务仍待实施，设计见 [渠道方案](chat01-provider-design.md)。

## 大文件与十种附件混合测试（2026-11-05）

用户授权测试 100 MiB HTTPS、失败后一次 Base64 对照、再测 50/75 MiB，并要求十种各 10 MiB 的附件。用户明确绕开 20808：所有请求使用 `trust_env=False`，SSH 关闭外部配置、代理命令和 agent；本机连接检查未出现 20808。没有调用 Pro。这里的 MiB 均为 1,048,576 字节。

### 单文件

100 MiB 合成 ZIP 使用 ZIP_STORED 和随机载荷，不靠压缩把名义 100 MiB 变成小传输。初次 localhost.run 隧道只写出部分内容，约 60 秒后中断并被上游重取。该隔离原型对两次完整下载额度做了预留限制，第三次 GET 被原型返回 429；因此本次失败不能用于判定 Chat01 文件上限。无模型调用的对照：本地 1 MiB 下载 0.02 秒，公网同段传输在 87.95 秒时仅交付 720,896 字节，随后主动停止诊断隧道。该对照明确表明该临时路径不适合大文件验收。

同一 100 MiB 文件按用户明确指示补测一次 Base64：使用分块编码并设置准确 Content-Length，没有同时在内存保留整份编码和 JSON。完整请求 139,810,673 字节，约 8.3 秒返回 HTTP 413，HTML 错误页标记为 Cloudflare。不能据此反推出精确的请求体上限或 HTTPS 文件上限；也不能确认该失败实际是否扣费。

改用 [Pinggy HTTPS 隧道](https://pinggy.io/docs/http_tunnels/) 后，先以 1 MiB 范围下载验证原件哈希（约 2.09 秒），再进行以下独立调用：

| 文件 | 模型请求体 | 完整发送文件耗时 | 原件核验 |
| --- | ---: | ---: | --- |
| 50 MiB ZIP | 993 字节 | 约 8.55 秒 | 大小、SHA-256、随机标识全部匹配 |
| 75 MiB ZIP | 998 字节 | 约 12.32 秒 | 大小、SHA-256、随机标识全部匹配 |
| 原先同一份 100 MiB ZIP | 994 字节 | 完成的一次约 51.08 秒 | 大小、SHA-256、随机标识全部匹配 |

100 MiB 复核的第一次 GET 在约 60 秒中断，随后在同一次模型请求内重取成功；未因此再次 POST 模型接口。它证明本次 HTTPS 单文件至少支持 100 MiB，不证明最大值恰好 100 MiB，也不核实用户提及的 200 MB 是单文件或总量。

### 10 个文件，每个 10 MiB，总计 100 MiB

一次请求包含 PDF、DOCX、PPTX、XLSX、PNG、JPEG、WAV、MP4、ZIP、TAR。每份精确为 10,485,760 字节，合计 104,857,600 字节；图片走 `image_url`，其余走 `file_url`。样本均为合成文件，使用格式允许的填充结构控制大小，并通过 pypdf、Office 对应读取库、Pillow、wave、OpenCV、ZIP/TAR 检查。测试验证原件运输，不宣称密集内容的语义理解或预览全面通过。

结果通过：

- API 请求 JSON 仅 3,541 字节；一次 `gpt-6-thinking` POST。
- 十份文件在来源端均完整返回，流式计算的 SHA-256 与本地基准一致。
- 模型通过代码读取后报告的十份原件 SHA-256 全部匹配，包含 PNG/JPEG，未观察到图片原件被重编码；大小和总量也已核对。
- HTTP 200、`[DONE]` 与完整原件证据同时满足，才判定成功。
- 下载中有三次失败重取，实际累计写出 126,353,408 字节；逻辑附件总量仍为 104,857,600 字节，额外 21,495,808 字节属于重取开销，不重复占用附件数量/总量预算。

整个探测用时 364.24 秒，不能把它当成上传 100 MiB 的正常带宽基准。按来源日志拆分（四舍五入，文件间间隔不能进一步归因于上游内部某个具体阶段）：

| 阶段 | 时间 |
| --- | ---: |
| 测试启动、鉴权/HEAD 预检，到首次 GET | 16.30 秒 |
| 十次成功 GET 的发送耗时之和 | 25.69 秒 |
| XLSX、JPEG、MP4 三次中断前的等待/部分发送 | 182.22 秒 |
| GET 之间的累计间隔 | 69.73 秒 |
| 最后一次 GET 完成，到模型响应结束 | 68.90 秒 |
| 结束后清理与关闭验证 | 1.40 秒 |

首次 GET 在 16.30 秒，十份原件全部送完在 293.94 秒，模型回答结束在 362.84 秒。即使扣除约 182 秒的三次失败等待，本次仍约三分钟，不能将全部耗时归为临时隧道；其中还包含上游串行准备附件、请求间隔与后续生成等无法进一步分拆的时间。测试使用的临时 SSH 隧道不会进入生产部署；生产速度需要以实际部署线路和上游行为观察。

本节共 6 次模型 POST（100 MiB 初测、Base64 对照、50/75/100 MiB HTTPS、10×10 MiB），按用户报价合计预留 12 分；失败调用的实际扣费未知。累计 18 次模型 POST：16 次 HTTP 200，其中一次是明确的附件准备失败；另有此前一次 400、本节一次 413。没有自动重发付费请求。

原始记录分别在 `.cache/chat01-probes/20261105/https-100m/`、`size-probes/`、`mixed-10x10m/`；每次都有结果与逐文件取件记录。临时服务、隧道已停止。本节未改变生产代码或镜像。
