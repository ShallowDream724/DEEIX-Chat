# Chat01 官网组件协议核对

2026-11-05。只读调查，用于补充待审核的 [首轮实施计划](chat01-implementation-plan.md)，未开始组件或供应商的生产实现。

## 证据范围

已读取官网公开入口引用的 [聊天前端脚本](https://chat01.ai/_next/static/chunks/133-dece0113d16b7320.js)，通过静态分析核对解码、校验、渲染与交互调用关系。未使用登录 Cookie，未发送聊天消息或消耗模型额度。

- 脚本原始 SHA-256：`009dbc43e13f627382eed24136a5b236472ef0390a02bd2e1df30a7073686f03`。
- 下列定位为该快照解码后的零基字符偏移，不是字节偏移。压缩符号只用于定位此快照，不作为稳定接口名称。
- 首次调查仅取得公开脚本。随后用户将 [组件枚举对话](https://chat01.ai/zh/chat/01M6N21DQNFD23HH0A8D47WXYZ) 改为公开，已通过无 Cookie、无代理的 HTTP 请求取得 200 响应，读取其服务端 HTML 与内嵌消息数据。没有实际操作游戏或按钮，另一个地图聊天页仍未读取。
- 公开页面原始 HTML 为 276,806 bytes，SHA-256：`672dc0a163a7b276abfa736adf278018fd5a2b2eb91de648b20949ce6ce24109`。网站数据与公开 API 的数据契约仍需区分。

## 已确认的格式与行为

| 位置 | 事实 | 对适配的影响 |
| --- | --- | --- |
| `K`，38976；`Z`，35392 | 消息尾部可携带 `\n\n<!--chat-ui:v1:` 标记，后接 Base64 编码的 UTF-8 JSON，以 `-->` 结束；校验顶层 `version: 1`、`nodes`、`states` 和可选 `runtime` | 可建立版本化解码器，正文与组件数据分开处理；不能把整个尾部当普通正文或只凭 HTML 外观判断 |
| 标签注册表 `U`，约 33031 | 包含布局、文字、链接、引用、图片、表格、图表及按钮、输入框、选择器、滑块等基础节点 | 使用受限节点注册表与通用渲染适配，不按每个页面、小游戏逐个编写 |
| `V`，37494；`eu`，49991 | 专用 widget 定义有六类：`formula`、`code`、`writing`、`app`、`map`、`chart`，分别校验字段与大小 | 这是该脚本的专用类型集合，不等于所有可能交互产品的完整清单 |
| `__chatgptClientDefinedWidget` 分支，约 74563 | 根据 invocation ID 从 `runtime.widgets` 查找定义，再进入专用渲染器 | 只有调用 ID 而没有字典内容时，不能还原组件 |
| 地图渲染器 `es`，44788 | 使用地点名称与实际经纬度绘制 SVG 点位图 | 地点内部引用不足以恢复坐标；不能据此承诺还原官网完整地图或地理底图 |
| `runtime` 校验与执行路径 | 接收 `code`、`constants`、`appData`、可选 `widgets`；另有 `DIL` 状态/渲染接口及 `opGenui` 数据解析 | 基础节点有限，但代码组合出的应用行为不适合逐项枚举；完整运行时兼容是独立工作量 |
| `ed`、`e0` 与运行时模板，约 48100、114283、91885 | 应用运行于隔离 iframe，动态运行时还使用 Worker、消息校验、超时与心跳；存在静态节点回退 | 不能把上游代码直接放进 DEEIX 页面执行。可复用现有隔离设施，但现有设施并不自动具备 DIL 协议兼容性 |

官网校验器本身限制节点数、深度、字符串与运行时代码大小。DEEIX 应在专用解码边界采用明确上限，保持增量解析有界；不需要复制官网整套前端。

`K` 在标记存在但载荷不完整或不合法时会只返回标记之前的 Markdown。我们的处理不能照搬这一信息丢弃行为：有效正文保留；有可读内容则保留可读内容；无法解码的组件记录有限诊断信息与未支持状态，不无限缓存，也不把大段 Base64 展示给用户。

## 交互是否直接发送消息

已确认这份官网前端的组件 prompt 回调连接到输入框状态：

- `tn`，130018：`[f,b] = useState("")` 保存输入文字；`x` 保存运行中状态。
- 消息渲染，146420、148101：`onPrompt` 在只读或运行中为禁用状态，其余情况传入输入框 setter `b`。
- `e1`，120103：向组件渲染继续传递该回调。
- 动态运行时 `GenUI.issueNewTurn`，93315：在交互事件内产生 prompt，主页面接收后调用上述回调。
- 独立提交处理器 `eF`，约 136556：检查登录、输入、额度后才 POST `/api/ai`，提交时清空输入框。

因此，不能因函数名叫 `issueNewTurn` 就认定它自动产生一次付费请求。这条调用链实际填入输入框，用户仍通过正常发送动作提交。

DEEIX 首版对已支持的同类动作采用相同语义：进入共享草稿入口，由用户发送；已有草稿不得被静默覆盖。按钮改变本组件本地状态无需模型请求。只有拿到 API 实际动作载荷且能确认语义的控件才启用，不将任意回调或缺少官网会话状态的动作伪装成可用。

## 公开对话中的真实载荷

从 Next.js 页面内嵌消息数据提取出两段有效 `chat-ui:v1`，只解码 JSON，没有执行其中的代码。原始页面、解码载荷和代码留在本地调查缓存，不提交第三方运行时代码或整份用户会话到仓库。

| 样本 | 已取得数据 | 对适配的影响 |
| --- | --- | --- |
| 第一段组件演示 | `nodes=[]`，12,562 字符运行时代码、48 项 constants、1 个 map widget，含 4 个地点的名称、地址与经纬度 | 井字棋、猜数字、滑块等由 DIL 状态与代码组合产生，不能仅把空 nodes 映射到共享控件就宣称完整支持 |
| 第二段组件陈列 | `nodes=[]`，31,824 字符运行时代码、279 项 constants，3 个 widget 分别为 map、code、app | 官网确实将常规组件、专用地图和内嵌 HTML/JS 应用组合在一条回答中；完整复现需要运行时兼容，不只是类型枚举 |
| 第二段资源解析结果 | `opGenui.componentResults` 含 AsyncImage、AsyncImageGroup、Entity、Link、Cite、FollowUp 的已解析数据 | 图片来源、引用和后续问题有结构化数据可以复用；不能只抓正文 URL 而丢掉关联信息 |
| FollowUp | 同时给出显示文字 `value` 与实际提示 `query` | 展示与填入草稿的内容应使用各自字段，不能拿显示标题替代完整 query |

样本还暴露出两个需区分的问题：

- 第二段地图中的“太空针塔”保留西雅图地址，却提供 `lat=39.953776, lon=116.474109`；这是载荷内部的不一致。适配器不得为它猜坐标、编造路线或假装完成了地理核验。第一段同名地点提供的是西雅图坐标，两段不能按名字合并。
- 第二段代码调用 `GenUI.copy`，而已核对的官网运行时 `GenUI` 对象只见 `issueNewTurn` 实现。未执行按钮，不宣称已复现点击失败；该静态不匹配说明模型声称“可交互”不等于每个动作都可用，兼容层需要按实际支持的动作判断。

搜索配图的解析结果包含图片检索词、原始网站与图片地址。即使 URL 来自 `images.openai.com`，也不能将其自动认作生成图片、生成文件或计费的 image_generation 调用。统一资源描述应保留来源类型。

页面的消息序列同时包含阶段性 assistant 回答和存放思考文本的 tool 记录；这不授权本地再次执行工具。网站字段只帮助理解展示，API 仍按真实返回结构单独解码。

## 对首版实施范围的修正

1. Chat01 输出适配器先识别并保留组件边界，采用独立、带版本的组件描述；有完整数据时才映射共享展示组件。与 DEEIX 提示词驱动组件开关完全分离。
2. 首版优先处理已有 API 样本中的可读地点、引用、图像、文件及其他有完整数据的内容；不假装内部引用已经解析成地图。
3. 新的声明式节点与已知数据组件按注册表扩展，可复用现有样式、表单、图表及草稿分发。官网协议解码留在 Chat01 模块，通用消息组件不认识其私有字段。
4. 带 DIL/任意应用代码的完整兼容不混入附件主线。官网完整样本已取得，但还需确认 API 是否交付同样的 code、constants、appData 与 widgets，再决定隔离执行、状态恢复和资源访问实现；当前保留可读内容及局部未支持状态，不让单个组件损坏整条回复。
5. 不新增付费探测来重复证明附件大小；后续如确需补组件样本，只围绕缺失字段做小规模定向验证。普通 HTML 代码块仍按原有行为处理，不冒充原生组件验证。

以上将首版承诺限定在有证据、可验收的行为，同时保留接入完整组件载荷的接口。
