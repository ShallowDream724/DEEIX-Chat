# 原生附件发送与就绪状态

本扩展让已经上传、可由当前模型原生读取的附件直接参与请求，不等待后台文本提取。复用原有上传、存储、解析、路由授权和计费流程，不增加数据库迁移。

## 职责与流程

- 原生资格和请求预算统一由会话服务的 `native_input.go` 判断。客户端不维护厂商能力或容量规则。
- `POST /api/v1/files/native-readiness` 是只读预检：复用模型权限、文件所有权和个人渠道授权；平台模型取所有候选渠道的能力交集，不选择 API Key、不占用熔断探针、不发起模型请求。
- 发送时按实际渠道重新判断，并在等待解析之前读取有界原文件。读取成功后跳过该文件的文本等待、全文和 RAG 注入；独立知识库检索保持原有行为。
- 后台解析照常运行。原生资格是当前模型、会话和附件组合的临时状态，不写入文件记录，也不把文件的解析状态伪造为完成。
- 当前版本没有音视频的解析上下文链路。本轮音视频附件在当前模型不支持原生输入时，以 `file.model_unsupported` 阻止生成；历史附件保持既有上下文兼容行为。
- 故障转移后若原生文件无法继续携带，本次请求明确停止并报告文件未就绪。用户重试或更换模型时重新规划，走需要的原生或解析路径；不在已经执行中的一次请求内另建全文/RAG 回退流程。

## 预检接口

请求：`{ "model": "平台模型名", "fileIDs": ["文件ID"], "conversationID": "可选会话ID" }`。

响应：`{ "files": [{ "fileID": "文件ID", "eligible": true }] }`。不可用时可返回 `unsupported`、`budget_exceeded` 或 `unavailable` 原因；权限和非法文件引用沿用既有 HTTP 错误。正常状态不附加解释文案。

客户端上传完成、切换模型、增删附件及提取终态改变时批量刷新预检；合并短时间内的变化，取消过期请求，切换组合立即失效旧结果。预检不可用时保留现有附件状态，实际发送仍以服务端校验为准。

输入框内切换到不支持原生 PDF 的模型时，已解析文件使用现有全文或 RAG 链路，未完成解析的文件恢复原有处理状态并在发送时等待。切回支持原生的模型后重新检查原件与预算，无需重新上传；原生选择不修改持久化的解析状态。

## 容量规则

| 路径 | 原生输入预算 |
| --- | --- |
| 官方 OpenAI Responses / Chat Completions PDF | 单 PDF 小于 50,000,000 字节；原生文件合计最多 50,000,000 字节；不额外设置统一 PDF 页数限制 |
| OpenAI Chat Completions 音频 | 保留原有音频格式与非 PDF 的 14 MiB 保守限制 |
| Gemini GenerateContent PDF | 单 PDF 最多 50,000,000 字节；PDF 合计最多 **200 页**，这是本扩展的保守限制 |
| Gemini GenerateContent 全部内联输入 | 原件预算按 Base64 膨胀计算并预留结构空间；最终完整 JSON 请求体不得超过 100,000,000 字节，包含历史、图片、工具和文本 |
| 其他协议 | 保留原有保守预算 |

有页数限制的路径遇到页数未知的 PDF，复用已有内置 PDF 页树探测，不执行 OCR 或全文提取。探测失败时不声明原生可用。原件读取同时核对实际字节数，避免数据库元信息与存储对象不一致而绕过预算。

上述预算不绕过后台单文件上传限制、用户累计存储配额或模型上下文限制。Gemini 的 100 MB 是编码后请求体上限，不等于允许 100 MB 原始音频。

依据：[OpenAI 文件输入](https://developers.openai.com/api/docs/guides/file-inputs#usage-considerations)、[Gemini 文件输入](https://ai.google.dev/gemini-api/docs/generate-content/file-input-methods)、[Gemini PDF](https://ai.google.dev/gemini-api/docs/generate-content/document-processing)、[Google 内联容量说明](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-api-new-file-limits/)。

## 客户端显示

沿用原附件卡片和删除按钮布局，仅在第二行处理状态位置显示绿色“原生”。标签整体高 12 px，内部文字 10 px、正常字重，水平和垂直居中，上下各留约 1 px；相邻元信息保留 11 px，避免标签因同字号再叠加内边距而显得突兀。标签不收缩，后续类型与大小沿用现有尾部省略。原生与提取转圈互斥，原生可用时后台提取失败不覆盖该状态。

不新增文件名、原生或提取状态的悬浮解释，不增加切换按钮；保留原有附件预览、移除提示和其他已有交互。图片不增加标签。临时聊天保留其独立附件链路，不声明本扩展的原生就绪状态。Web、桌面 WebView 和手机浏览器复用同一组件。

## 镜像迁移

复用上游 Dockerfile 和 Image 工作流构建，不引入第二套打包流程。部署时替换应用的 `image`，保留现有 `/app/storage` 卷、数据库连接、配置文件和 Redis。使用固定镜像版本，记录原镜像 digest 便于回退；本扩展不主动清理用户文件，也不改变文件保留策略。

Image 工作流的手动触发可选择 `amd64`、`arm64` 或 `both`；默认和原有推送触发仍构建双架构。只面向一台服务器发布时，选择该服务器架构以减少构建用量，继续复用原有缓存和 manifest 发布步骤。

上游同步时，集中检查原生策略、发送前准备、路由预检和附件状态组件四处接入。后续新增渠道应扩展同一策略边界，不复制上传、权限或计费系统。
