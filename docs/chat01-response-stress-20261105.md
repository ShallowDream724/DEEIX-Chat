## 实际发现与修正

- 上游把 Thought 标题直接粘在截断的 Python 表达式前，或把命令结束与下段标记粘在一起。增加过程区内的命令、heredoc 和相邻代码行识别，缺调用边界的内容标为“执行片段”。
- WAV 样本含残缺加粗标题尾部。旧规则会把后续结束标签和整段最终回答吞进思考；现限定标题起点，并保护 Python 的 `**` 运算符。
- 教程样本会在行内代码、四反引号/波浪线围栏、Python 多行字符串中原样讨论 `<think>`、`## Answer:`。这些是答案内容，不能作为协议边界；已加入对应保护和回归。
- 独立审查构造畸形文件名 `%ZZ` 复现 URI 解码异常。资源提取现在容忍该文件名，并跳过不能解析的 URL；正文和同轮有效文件继续保留。此项是合成边界，不声称上游已实测返回。
- 所有修正位于独立分类核心及资源识别器，没有在显示层用另一套正则重新分段。输入位置、原始字符保留供对照；不执行返回的代码。

代码任务要求多次执行，响应确有多段命令与产物，但缺少完整 per-call 结果，不能把“要求六次”当成“观察到六个完整工具调用”。同样，不把 `print(...)` 命令当作已经收到 stdout。

## 文件本地核验

下载九份测试产物，共 20,295 字节；没有重跑返回的脚本。

- 项目 ZIP 的 CRC 检查通过，十个成员的哈希和大小与报告一致；原 CSV 与上传 ZIP 内的同一成员一致，24 行数值合计 1,373。返回测试日志显示四项通过，但这是上游日志，不冒称本机执行了该程序。
- Office/PDF 报告中的三份源文件哈希与本地基线一致：DOCX 36,680 字节、PPTX 28,298 字节、PDF 1,426 字节；报告 ZIP 的 CRC 检查通过。
- 音频报告核对 8,000 Hz、4,000 帧、0.5 秒；修复后的 JSONL 保留三条有效记录，单独记录第三行坏数据，源文件哈希一致。
- 音频样本正文中有三个有效 CDN 文件链接和一个未替换的 `sandbox:/mnt/data/repaired.jsonl`。API 没有可用容器映射，不能凭此路径下载。修复后的 JSONL 确实包含在可用 ZIP 中；这不等于那个独立地址已修复。

生产方案据此采用逐文件状态：不让一个坏链接使整批文件失败，不根据文件名猜 CDN，不把 Chat01 sandbox 路径交给 OpenAI 容器 API。

## 官网组件与 API 的差距

专项任务仍没有返回官网公开页中的完整 `chat-ui:v1`、`runtime.widgets` 或 `appData`：

- 地图 `map_widget_v2` 只有内部地点 ref 与标题，没有坐标；正文另有地点和地址，可展示可读信息。
- 计数器和后续问题只有文字，没有可执行动作或状态；表格只有表头，没有数据行及排序行为。
- 搜索照片只给了 Wikimedia 网页 URL，未提供图片 URL。网页链接不能放入 img 冒充预览；有真实图片地址时才按确认的外部来源预览政策展示。

所以存在“API 返回组件痕迹，但缺少渲染所需数据”的具体样本。首版保留已有信息，不伪造交互；此批结果不证明 API 永远不能返回完整组件，也不要求移植官网动态运行时。

## 提示词与长任务

字面量教程请求的 system 字段带唯一测试末尾词，回答按 Markdown 转义后输出该词，证明该字段在该次请求中能影响结果。根据用户说明，Chat01 将 system 转成官网前置消息；该探针不证明其具有 OpenAI 原生 system 角色的优先级。实施重点是按来源减少无用内容，而不是删除所有 system 字段。

源码核对发现 Skill 默认包装禁止调用未由本站显式提供的工具，这可能干扰官网 Agent。所选技能正文继续有价值，默认包装需按实际渠道能力精简；MCP 禁用，官网服务端工具保留。用户开启的少量偏好可沿用现有约 400-token 上限；额外个人资料/自定义记忆和广泛召回在 Chat01 默认关闭。完整策略及普通/临时/重试共用边界见[实施计划](chat01-implementation-plan.md#34-提示词与功能边界按最新用户说明拟定)。

9,000 秒空文本心跳是离线解析器模拟，无真实等待和 Pro 请求；不代表两小时 HTTP、代理、后台恢复或取件授权已经测试通过。新渠道建议 150 分钟读取/流空闲预设，集成时共同核验任务与授权期限。通用标题问题仍未修复，继续排在 Chat01 之后。

新增真实缺陷及修复：
