# 附件限制与图片处理方案（待确认）

调研日期：2026-11-04。本文是方案，不表示功能已实现或已批准开发。代码现状以 `0d473855` 及其已提交功能基线为准，不采用工作区暂停的实现草稿。用户截图中的数值作为本次建议的迁移起点；未读取线上数据库验证是否已保存。

## 1. 截图中的设置应表达什么

现有界面标注 MB，但上传和全文大小按 MiB 换算。迁移保留原始字节值，改正显示单位，不把 50 MiB 静默变成 50 MB。

| 设置 | 截图值与当前意义 | 已确认的文案范围与待确认行为 |
| --- | --- | --- |
| 附件数量上限 | 20，限制单条消息新增附件 | 保留现有标题和说明，不作无必要重命名 |
| 默认大小上限 | 50 MiB，单个上传文件上限 | 保留现有标题和已解释清楚的描述，不因图片优化而自动改变默认文件额度 |
| 图像大小上限 | 50 MiB，单张上传原图；当前与默认值取较小者 | 标题保留，只改描述，删除“单独覆盖”。撤回“图片建议继承50 MiB”；图片硬上限与3 MB优化目标分开讨论 |
| 文档大小上限 | 50 MiB，单个 PDF/Office/文本等文档；当前与默认值取较小者 | 标题保留，只改描述，明确单个文档；空白表示使用默认值。不是 PDF 原生发送预算 |
| 音频、视频分类 | 无独立分类字段，使用默认大小 | 增加单个音频、单个视频上传上限，初始继承 50 MiB |
| 用户存储配额 | 1024 MiB，即 1 GiB，所有持久化用户文件合计 | 标题和描述保留，保持 1 GiB；已占用、剩余可显示给用户 |
| 全文大小/Token/页数 | 1 MiB、272,000 tokens、200 页；解析后单文件全文的准入条件，同时生效 | 三个标题保留，只在描述中补充单个文件/单个 PDF；保持用户值 |

已确认的描述调整草案（页面单位最终按统一的字节显示方案处理，此处沿用现有 MB 文案）：

- 图像大小上限：用于设置单张图像附件的大小上限，页面单位为 MB；留空时使用默认大小上限。
- 文档大小上限：用于设置单个文档附件的大小上限，页面单位为 MB；留空时使用默认大小上限。
- 全文大小上限：用于限制单个文件全文注入时的提取文本大小，页面单位为 MB；留空或填 0 表示不限制大小。
- 全文 Token 上限：用于限制单个文件全文注入时的 Token 数量；留空或填 0 表示不限制 Token 数量。
- 全文页数上限：用于限制单个 PDF 全文注入时的页数；留空或填 0 表示不限制页数。

不同维度的限制同时存在是正常的运营选择，管理员负责组合；不强求上传、原生、全文和模型窗口数值一致，不自动同步、放宽或清空管理员设置。说明作用范围与实际触及哪项限制即可。分类字段的继承语义必须明确，不能以“默认值”文案暗中表达一个永远不可超过的全局硬上限。

当前全文准入只对 PDF 额外检查页数，是因为当前提取链路只为 PDF 获取并使用 `PageCount`。Word/PPT/Excel 并非不限，仍共用单文件提取文本字节/token门槛。PPT的幻灯片数可以增加，但当前未实现；Word实际分页依赖排版环境，不能把没有可靠页数的数据伪装成统一页数。若未来限制PPT处理工作量，使用明确的幻灯片数，不套用“PDF页数”。

例如一个 40 MiB PDF 可以上传，也可能走原生读取，但若提取文本超过 1 MiB，仍可能不符合全文注入条件。1 GiB 存储配额不放宽任何单文件或模型请求限制。50 MiB 为 52,428,800 字节，超过官方 OpenAI 单个 PDF 小于 50,000,000 字节的要求；上传文件库和选模型发送分别预检并解释，不能据上传成功显示所有模型均可原生读取。

## 2. 长图调研结论

长图可以作为图片输入，但可读性受模型、图像预处理、文字大小、分辨率预算和任务影响，不能用“接口接受了图片”证明所有文字可读。当前 DEEIX 将最长边固定缩至 1024 px，对长截图尤其不利：1080×12000 会缩成约 92×1024，20 px 的字高度约剩 1.7 px。

当前本地处理保留存储原件，只改变发送副本；缩放使用最近邻，PNG 输出 PNG，其他支持格式输出 JPEG 质量 85。用户端没有本地缩放开关，后端的 `file.image_max_dimension` 未暴露在管理员页面；普通会话及图片 MCP 路径把 0 改回 1024，临时会话才正确支持 0 不缩放。

### 官方公开做法

| 供应商 | 公开文档事实 | 对 DEEIX 的含义 |
| --- | --- | --- |
| OpenAI | `detail` 支持值依模型而异。部分模型支持 `original`，旧模型常用 `high`/`auto` 的分块和缩放规则。当前 GPT-6 Astra 的 `original` 仅按最大边 65,535 px 缩放，处理后超过 30,000 patches 则拒绝；GPT-5.4 的 `original` 又有 6,000 px 和 10,000 patches 预算。官方明确提示小字、全景图有识别困难 | 必须按实际模型声明参数和计量；不能将所有模型预先压成 1024，也不能把 `original` 宣称为供应商永不缩放 |
| Gemini | 媒体分辨率控制分配给媒体的 token；当前 Gemini 3/4 文档建议图像 `high`，PDF 通常 `medium`。支持按内容项设置的模型可分别指定；默认和参数支持范围随模型/协议不同 | 复用已有聊天参数中的媒体分辨率入口，补齐适配范围；图片、PDF、视频不要因为一个“高清”选择全部统一抬高。高分辨率不能恢复已被本地缩坏的图片 |
| Claude | 当前文档区分高分辨率模型与标准模型；Claude 4.7 及以后给出最长边 2576 px/4784 visual tokens，其余标准档为 1568 px/1568 tokens；超出会缩放。官方建议避免重压缩和过小文字，必要时 resize/crop | 即使本站原图发送，上游仍可能缩小长图；可提供有顺序和重叠的局部读取，保留全图参考 |

以上是公开 API 行为，不推断 ChatGPT/Gemini/Claude 网页端未公开的完整处理流程。未进行付费模型可读性测试；分段方案和默认参数仍应在实施阶段用用户实际渠道验证。

### 需要纠正的供应商限制认知

- OpenAI 当前视觉文档为每请求 512 MB、最多 1500 图；PDF 文件输入仍单个小于 50 MB、文件合计 50 MB。这些条件同时检查，不把 PDF 预算替换成 512 MB。
- Claude 当前第一方 API 文档为请求 128 MB、最多 600 图、单图 10 MB（Base64 编码后的计量）。PDF 文档为最多 600 页；请求上下文窗口不足 1M tokens 时最多 100 页。第三方托管平台限制可能不同，不能继续把旧 32 MB/100 图套到所有 Anthropic 协议渠道。多于 20 图还会触发更严格的单图尺寸条件，需按实际模型/平台验证。
- Gemini 官方文档存在需核对的口径：文件输入方法页写 inline 100 MB/request（PDF 50 MB），图像理解页仍写完整 inline 请求 20 MB。后者现已使用 Interactions 示例，但文件方法页又描述多端点适用，不能仅据示例断言二者区别已得到证实。当前 GenerateContent 100 MB 本地值暂保留、注明来源与待验证项；不能在本次方案中无证据改成全渠道 20 MB，也不把 100 MB 宣称为所有端点的保证。
- Gemini PDF 文档写 50 MB/1000 页；本站既有 200 页是应用运营策略，建议保留为管理员可调值，不称为供应商硬上限。

已存在的聊天模型参数面板支持 Gemini `generationConfig.mediaResolution`。它是上游媒体处理参数，与本站上传或缩放不同；新入口应映射到同一参数来源，避免两个控件设置相互覆盖。

模型输入预算与渠道值属于同一组字段的默认/特例关系，不是两个连续扣减的预算池。先选出该渠道继承或指定的值，再与供应商/模型真实限制共同检查。例：默认不额外截历史图片，Chat01指定全请求10图；切到其他渠道不继承Chat01的10图。编辑时清楚显示“使用默认”或“使用本渠道值”。

该编辑器拟提供：完整请求大小；本次请求图片数；处理后单张/合计图片大小（明确编码前后口径）；原生文件数量与原件合计；PDF单个/合计大小和合计页数；音频/视频适用的单个/合计大小。仅显示所选协议实际支持的项，生图/视频参考图条件按任务类型显示。上传单文件限制、图片压缩目标、用户存储配额、解析全文门槛不在这里重复设置。

## 4. 图片处理建议

### 上传硬上限、压缩目标与性能

当前上传前端先按原始 `File.size` 校验，后端再限流保存原件；缩放在之后发给模型时执行。所以单张图片上传上限不会触发自动压缩，把该值设成3 MB会直接拒绝超过它的原图，不能指望后面的缩放救回来。

按用户反馈修订建议：日常优化目标3 MB，超过5 MB触发优化；这两个新参数按明确显示的单位保存。上传硬上限是另一项接纳/资源边界，不再建议把50 MiB当作日常图片目标。可讨论20 MiB作为原始图片接纳上限，但尚未定值或修改现有设置。

- 不把大文件一概归因于元数据。冗余EXIF、内嵌缩略图可清理，但高像素、纹理噪点和无损编码也会产生真实体积；须正确应用或保留方向和色彩信息，不能直接删除所有元数据造成旋转或偏色。
- 优先轻量优化和合适编码，保持文字/图表可读性；必要时才有损编码或降采样。PNG不等于截图，JPEG不等于照片，不能仅凭扩展名决定有损策略；不为分类额外调用大模型。
- 已小于目标的图片默认不重复有损编码。超过目标但不超过触发值时可保留或做轻量优化；超过5 MB再按有限的编码尝试趋近3 MB。目标大小不是保证值，长图/密集文字不为凑数无限降画质；未达目标但符合硬上限可以提示后保留。
- 优先评估浏览器Worker预处理，减少上传流量和服务器编码工作；浏览器不支持、超大画布、方向/色彩处理无法保证时显式回退。服务端仍独立验证文件类型、字节和像素，不能依赖客户端保证。
- 如采用上传前优化，服务器保存的是优化后文件。保留上传原图需用户另选原图或明确保存双份，不能仍声称默认服务器保留未压原件；这项存储行为待确认。现有历史原件不做追溯替换。
- 服务器需要处理时使用有限任务并发、像素/内存边界、有限编码尝试，并按文件哈希和处理参数复用结果。禁止每轮重压、所有格式并行试一遍或为了极少字节使用高成本穷举优化。

成熟库可参考：browser-image-compression提供Worker、目标大小、保留分辨率和最大迭代数，但canvas路径本身可能缩放或重编码；Sharp/libvips提供元数据控制、缓存和每图线程数控制。它们证明这些控制有成熟实现，并不证明直接套默认值就能保持文字保真或符合DEEIX性能目标；是否引入具体依赖仍需小规模基准。

### 面向用户的三个档位

| 档位 | 本地处理 | 上游参数 |
| --- | --- | --- |
| 自动（建议默认） | 取消全局最长边 1024；依据已验证模型处理规则和请求预算决定是否有必要预缩放。未知模型不盲目降采样；长图优先保留并提示分段 | 按实际模型支持采用 auto/默认；已知文字密集或用户明确选择细节时可采用相应精细档，不能凭 MIME 猜测内容 |
| 保留细节 | 本站不主动有损缩小；不满足供应商尺寸/请求限制时显示原因和处理选项 | 支持时使用 OpenAI original，否则 high；Gemini 图像 high；不支持该参数的协议不伪造参数 |
| 节省用量 | 使用管理员可调的缩放配置；初始最长边建议 2048，PNG/文字内容优先保留无损编码。只在需要有损编码时采用可调质量，初值建议 90 | 选择实际模型支持的较低成本档；按模型计量，不假定所有模型的 low 都更便宜 |

“保留细节”只承诺本站的处理方式，不承诺供应商原样分析。编码质量和像素尺寸影响文件体积，视觉 token 还由模型规则决定；不能把 JPEG 变小直接当作 token 必然减少。缩放算法改为适合降采样的高质量算法，不继续使用最近邻。

管理员可调整：默认档位、允许的用户档位、优化目标大小、优化触发大小、缩放最长边（0 表示本站不缩放）、输出格式策略、JPEG/WebP 质量、长图识别条件、分段尺寸/重叠和单图最大分段数。相关参数只在对应模式下显示，不设置笼统的“高级”总分组。

### 长图分段建议（参数为待验证的初始值）

- 长宽比达到 3:1 且长边超过 2048 px 时提示“可分段读取”；阈值可由管理员调整，不凭比例断言图片含文字。
- 初始采用有重叠的顺序片段，建议片段最长边 1536 px、重叠 128 px、单图最多 16 段，均可配；保留一张全图概览，标注每段方向、顺序和原图区域。是否保留概览可配。
- 例如 1080×12000 可形成约 9 个局部片段，另有 1 张概览；这是 1 个用户附件、10 个模型图像内容块。显示与预算必须分别表达，不能把它显示成用户上传了 10 个文件。
- 供应商模型内部 tiles/patches 与 DEEIX 主动切片不同。主动切片可能增加图片数量、token 和费用，应预检并告知；不能为 Chat01 的 10 图上限静默截掉末尾段。
- 第一版建议用户显式选择分段；管理员可允许“遇长图自动分段”，默认关闭，等实际模型可读性及代价验证后再决定是否开启。
- 重试和历史复用保存处理选择及原图身份，缓存按原图哈希和处理参数区分；分支仍引用原件，不能仅保留短期切片缓存。缓存失效后从原件重建。

## 5. 写死预算的现在与改后

所有直接影响附件接收、处理和提供给模型的运营上限都给出管理入口。能由统一策略派生的 HTTP 大小不另建一套互相冲突的可写阈值，界面展示计算后的有效值。

| 项目 | 现在 | 建议改后 / 初始策略 | 配置位置 |
| --- | --- | --- | --- |
| 历史图片数量 | 最近 10 张，较早图片不提供 | 取消历史专属 10 张；按实际渠道约束检查全请求图片，站点额外限额初始不添加；管理员可设 | 模型输入预算；渠道覆盖 |
| 历史图片合计 | 20 MiB，不含本轮普通图片 | 取消历史专属 20 MiB；本轮/历史/分段图使用同一媒体统计，受真实完整请求预算约束；可增加显式运营子限额 | 同上 |
| 单张图片读取 | 写死 50 MiB，当前路径可能截断 | 使用文件元数据及有效文件政策作有界完整读取；超限明确报错。独立运行保护若需要则显示真实有效值，不再截断后继续发送 | 上传限制；图片处理 |
| 原生文件数量 | 部分协议最多 5 个 | 供应商明确数量限制照用；其他渠道取消无来源的 5 个默认，只受站点单消息数、文件大小、上下文和完整请求限制。可设运营上限 | 模型输入预算；渠道覆盖 |
| 原生总量 14 MiB / PDF 8 MiB | 兼容协议等共用保守常量 | 官方渠道按已核对文档，不把 14/8 MiB 当供应商上限；未知渠道将现值作为显式迁移保护值，管理员可清除或调整，未验证不一键放开全部渠道 | 同上 |
| 原生 PDF 单文件、总字节、页数 | 写死，且各协议不同 | 分开显示、按实际规则检查。OpenAI 保留单个 <50 MB/文件合计 50 MB；Gemini 保留 50 MB 和本站 200 页运营值；Claude 按当前模型窗口区分 100/600 页 | 同上；模型能力 |
| Gemini 原件总量约 74.2 MB | 固定预留 1 MiB 后反推，不含图片 | 用实际文本/工具/图片及编码开销计算可用空间，最终序列化兜底；保留供应商明确的文件子限额，不再以固定 74.2 MB 保证可以发送 | 模型输入预算（自动计算并显示） |
| 完整请求 | 仅 GenerateContent 100 MB | 每个适配器统一检查自身实际传输；官方 OpenAI 512 MB、第一方 Claude 128 MB；Google 现有 100 MB 暂保留并验证文档分歧；未知兼容渠道建议 100 MB 作为可见的站点初始保护值，允许按渠道改 | 模型输入预算；渠道覆盖 |
| 临时请求总附件 | 写死 20 个 | 独立显示为“临时请求附件总数”，初值保留 20，可调整；每消息数继承上传设置 | 文件与检索 → 临时会话附件 |
| 临时图片 10 张/20 MiB | 与普通会话另一套限制 | 取消，继承实际路由统一图片/完整请求预算 | 显示继承来源，避免重复设置 |
| HTTP 上传请求体 | 普通单文件上限+1 MiB；临时8 MiB+20×单文件上限 | 从类别有效上限、实际入口允许数量和协议开销派生；基础 JSON 预算8 MiB和临时总附件数在临时会话附件中可调；页面显示推导结果 | 上传设置只读有效值；临时会话附件 |
| 图片 MCP 合计20 MiB、分析文字6000/16000字符 | 内部常量 | 改为图片工具处理预算，保留现值作初始值，可调；控制外部图片工具的输入量和回传文本量，结果裁剪须记录 | 文件与检索 → 图片处理 → 图片工具（启用该功能时显示） |
| 图片编辑16张、xAI3张、视频参考图1张 | 应用/适配器写死 | 按端点与模型声明能力；运营数量可调，已验证供应商硬限不能用界面数字绕过 | 对应渠道/模型输入限制，区分聊天、生图、视频任务 |
| 编辑图片像素上限67,108,864 | 内部处理保护 | 显示为解码像素保护，初值保留，可调；限制解码后内存而非只看压缩文件大小，处理并发也放在同一处 | 文件与检索 → 图片处理 |
| 生成图片单文件50 MiB | 独立于上传的输出常量 | 增加“生成图片单文件保存上限”，保留50 MiB；控制从模型下载和保存的单个产物大小，区别于用户上传 | 文件与检索 → 生成文件 |
| 历史处理图缓存64项/64 MiB | 内部常量 | 增加项数、字节管理项，初值保留；缓存缩放/编码结果以避免重复CPU工作，淘汰后从原件重建，不代表模型遗忘 | 文件与检索 → 图片处理 → 处理结果缓存 |
| 提取/OCR服务读入与响应预算 | 服务中另有50/100/20 MiB等常量 | 控制读取的源文件/解析服务响应，防止上传成功却被内部读取截断；按服务配置，区分输入和返回文本 | 文件与检索 → 对应解析/OCR服务设置 |

额外运营限额关闭并不意味着供应商、文件类型或模型上下文限制关闭。继承用“继承”状态表示；“不增加本站限制”与“继承”明确分开，不让空值和 0 在不同字段里隐式改变意义。

每次实际发送至少分别统计：原件资格、选入模型上下文的媒体、实际序列化的传输字节。普通 inline Base64 计入编码体积；将来 Files API/file_id 路径不把原件大小错误累加为 JSON 大小。同一图片在实际内容块中出现多次时按协议定义计数；供应商内部切块不伪装成多个用户附件。

不默认上调已保存的用户运营限制；官方模板规则与站点运营值分开迁移。未知渠道默认值标注“本站保护值 / 待核实”，不能伪装成官方承诺。

## 6. 用户侧下放范围

下放：默认图片读取方式、单附件覆盖、长图分段选择、适用时原生/解析切换、现有全文/RAG偏好、上下文用量指示显隐、自己的已用存储与有效附件限制查看。高成本参数由管理员规定可用范围。

保留管理权限：上传大小/数量、存储配额、原生及完整请求硬上限、供应商能力覆盖、工作内存和缓存大小。用户选择原图或原生不能绕过限制；超限给出能执行的选择：取消部分附件、分段/降低清晰度、切换可用模型或解析方式。

“文件上下文”展示由同一发送计划产生：区分用户附件数、实际图片内容块数、历史/本轮、原生/解析，以及未发送原因。上下文使用量按当前有效输入快照更新；10k→11k→12k 时展示该序列，计费账目另行累计。

## 7. 待确认和实施前验证

- 已确认保留现有标题，只修订图像/文档与全文三个描述；默认大小上限、用户配额描述不改。文件与检索方向获认可，但不据此恢复所有暂停实现。取消“高级”总分组；预算集中编辑、渠道页只读摘要为本轮修订建议。
- 图片优化目标3 MB、超过5 MB触发来自用户偏好；上传硬上限、上传前优化是否替代服务器原图、具体编码器与性能参数仍需定稿。
- 建议默认自动、允许用户保留细节/节省用量；长图分段先显式选择。阈值3:1、2048、分段1536/重叠128/最多16段是产品建议，需真实阅读测试后定稿，不能引用为官方标准。
- 用中文长截图、代码、表格、票据和横向流程图，在用户实际 OpenAI/Gemini/Claude 渠道比较当前1024、原件、供应商清晰度、原件分段的识别结果、输入token、请求字节和延迟。没有这一步就不宣称自动策略精度已验证。
- 单独核对 Google 20/100 MB 文档差异、第三方渠道限额和非官方端点参数支持；不以模型显示名推断供应商规则。
- Files API 是后续候选优化，能减少原件反复传输；与 KV/prompt cache 分开，不作为本轮正确发送与分支保留文件的前置条件。
- 未确认方案前，不恢复暂停的功能开发，不发布镜像。
