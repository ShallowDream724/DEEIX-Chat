# Chat01 独立渠道适配方案（待实施）

本方案依据 2026-11-04 的 [API 实测](chat01-api-probe-20261104.md) 及用户后续明确的要求。当前阶段是验证附件传输和确定边界，尚未修改生产代码或构建新镜像。

## 用户看到的配置

- 增加 Chat01 供应商预设、地址和用户提供的 logo；其底层 GPT 模型的厂商信息继续保留 OpenAI，不改其他供应商行为。
- Chat01 默认使用专用适配方式，复用 Chat Completions HTTP/SSE 基础设施。内部 adapter key 区分方言，避免根据模型名或碰巧包含 chat01 的 URL 在多个模块散落判断。Responses 的 URL DOCX 原件输入也已验证；若保留该入口，与 Chat Completions 共用附件策略和内容规范化，只分离请求编码与事件封装，不重复维护两套业务逻辑。初版默认选覆盖六种附件的 Chat Completions。
- 该渠道的有效输入能力展示为“文本、图片、附件”。不再要求逐项开启原生 PDF/音频/视频来运输这些文件；文件原始类别仍保留，用于图标、预览、白名单、分类大小限制及其他渠道的能力判断。
- 所有非图片附件统一发 `file_url`；图片发 `image_url`，继续经过项目统一的图片处理和实际发送字节限制。接收原件不等于模型必然理解或能执行任意格式。

## 附件输入：共享规则，替换最后的序列化

继续走用户文件归属、有效文件状态、存储额度、上传白名单、分类大小限制、实际渠道预算和最终请求体检查。原件读取有界且完整，不能静默截断。Base64 和附件 HTTPS URL 均已有原件证据。2026-11-05 用户明确域名暴露不再构成约束，重点比较服务器负担与体验；针对 4C8G、本地存储和较大附件，当前建议以 HTTPS 附件链接为默认、Base64 为可控备选，待短期授权读取机制验证后实施。

通用文件原件需要独立语义：现有 `ContentPartFile` 代表提取文本，`ContentPartDocument` 当前按 PDF 处理，两者都不能直接扩大为任意二进制而不改其他约束。新增通用原件类型后，纳入数量、字节和上下文估算，复用现有文件缓存与预算统计。

Chat01 本轮选原件时，不等 MinerU，不重复注入同一文件的解析全文或 RAG；后台解析是否继续沿用既有设置。文件本身仍属于原用户轮次，切回其他模型时重新规划：可原生则原生，可解析则复用解析，不具备任何处理途径则沿用明确报错。Chat01 的能力不能永久写死在文件记录上。

数量口径需保留区分：当前 `messageFileCount` 是单条消息附件数，`imageCount` 是完整请求图片数，`nativeCount` 是完整请求原生非图片文件数。它们能继续生效，但不能代替“完整历史内图片与其他文件合计 N 个”。若供应商实际要求后者，再补明确的混合计数规则，禁止静默丢历史。

附件原名、实际 MIME 和大小要保留。Base64 无文件名字段的样本在上游变为 `.bin`；URL 图片样本实际为 PNG 却被命名为 `.jpg`。不能据此把 DOCX/PPTX 当未知文件或选择错误解码器，也不能承诺上游挂载名与原名一致。需要传递原始附件说明，并另行验证上游是否支持专用文件名字段。

追加实测中，`file_url.filename` 未解决 `.bin` 命名，Responses 的 `input_file.file_data + filename` 组合返回 400；不能当成已支持的修复。与此同时，约 1.1 MB 的 Base64 请求已成功完成含图 DOCX → 三页 PPT，数字、标识和原配图完整。该结果证明此任务可用，不证明所有解析流程零影响；没有 token usage，不承诺附件不占上下文。独立文件地址/presign 尚非项目现成功能，使用 HTTPS 前必须明确授权范围、文件名/MIME、过期和长任务读取行为。

### 2026-11-05：传输选型补充

- `.bin` 不作为否定 Base64 的理由：最近任务的用户提示没有明说源文件后缀，执行记录显示模型主动用文件头和 OOXML 结构识别、读取文档。请求仍携带 Word MIME 和 filename 字段，所以不是彻底去除类型线索的盲测；Chat01 到其上游的内部传递不可见。
- 两种方式的浏览器上传、站点保存文件及用户存储额度相同。差别在站点到 Chat01 这一段：Base64 约增加三分之一传输体积，并在当前实现中持有原始字节、编码字符串和序列化 JSON 等副本；编码本身不能与图片解码缩放的 CPU 成本混为一谈。
- HTTPS 链接使模型请求很小，文件由受限读取接口流式传输，避免把整份文件嵌进大 JSON。文件在本机时仍消耗本站出站带宽；仅当以后使用对象存储直达链接时，下载流量才可不经过应用服务器。
- HTTPS 多一次取文件操作，不保证小文件或每次模型任务更快。原测试的任务与文件不同，不能拿 221 秒与 164 秒当性能对照；也不假定上游会缓存跨轮文件。
- 新机制仅给本次已授权附件签发限时读取能力，复用现有存储读取，保留原文件名/实际 MIME，时效覆盖预期长任务取文件与必要重取；不能把普通需要登录的私有内容 URL 直接交给上游，也不公开整个目录。
- URL 请求体虽小，附件原始大小、数量、图片处理后大小等规则照常校验；不能利用 URL 字符串很短绕过真实附件预算。图片链接必须指向本轮实际应发送的处理结果，不能意外重新给上游发送未处理大图。

### HTTPS 授权读取的模块边界（2026-11-05，待实施）

已用独立本地单文件服务完成 HTTPS 与 Chat01 回取验证，详见探测文档。该原型不接入 DEEIX，不代表生产实现已完成。生产方案采用以下边界：

1. **共享附件规划**：普通与临时会话都先完成文件归属、白名单、实际渠道预算、内容版本与图片处理判断，得到可信的附件引用和元数据。HTTPS 路径不能先调用 `readNativeInput` 将整个文件读入 `ContentPart.Data`，再在序列化时替换成 URL；应从规划阶段保留引用，只有内联传输路径才加载字节。
2. **共享授权读取服务**：只接受经过规划授权的文件引用，签发限定文件/内容版本/发送副本/用途/本轮任务的短期读取凭证。建议用独立的附件授权缓存接口，沿用现有 Redis/memory 后端装配，缓存只有少量授权元数据，不存文件内容、不新增 SQL 表。复用缓存基础设施，不复用一次性 OAuth grant、登录 token 或公开会话分享权限。临时会话没有持久化 run 记录，也必须能通过同一服务签发与回收授权。
3. **独立下载入口**：凭证只授予这一份附件的读取权限，支持 GET、HEAD 与必要重取；每次都重新确认文件仍为该用户的有效文件，再通过现有 `Store.Open` 流式返回。删除/撤销后拒绝新的读取，已交付给上游的字节无法收回。URL 持有者可在有效期内读取，不把用途标记误当成上游身份认证。若支持 Range，必须限制范围数并以存储能力为准，不为 seek 将整个对象加载进内存。
4. **渠道适配器**：Chat01 仅选择适合的传输策略，并将地址放进 `file_url` / `image_url`；Responses 入口只更换字段与事件封装。后续其他供应商可以复用附件授权服务，但各家文件上传 API、file_id、URL 输入格式仍由其适配器负责，不强行统一成 Chat01 形态。

部署复用站点已有 HTTPS 反向代理与经过校验的 `PublicAPIBaseURL`；URL 不能从不可信 Host 头拼接。当前已有 HTTPS 的部署无需另建证书系统或安装隧道。独立文件域名可作为后续部署选项，不是第一版必填项。本地探测使用的临时隧道仅用于测试，不进入镜像或运行依赖。

生命周期与效率约定：

- 凭证按后端任务允许的最长运行时间加有限重取窗口设置有效期，不依赖浏览器是否仍停留在页面；正常结束、取消与异常退出分别回收/到期兜底。不能用一次取用立即失效的链接。跨轮重发按当前权限重新签发，不在历史消息持久化可直接取件的 URL。
- 采用可撤销、可重复读取的短期授权，优先缓存随机不透明凭证的摘要；记录绑定用户、文件版本、任务、用途和期限。首版不需要给用户增加一组签名密钥配置。缓存不可用时明确失败，不扩大成公开地址。
- 原件经固定大小缓冲流式传输，设置有界并发、读取超时与连接取消；吞吐和带宽仍受服务器及上游网络限制。图片解码缩放依然有开销，不能承诺 HTTPS 消除该开销。处理后图片以原件版本和处理参数定位受控副本，重取复用，临时副本有容量与生命周期约束；未来浏览器处理后上传同样接入此边界。
- 当前 `ValidateInputMedia` 用 `len(part.Data)` 计费前的附件预算测量，引用路径必须改为从服务端确认的实际发送大小统一取值，不能因 Data 为空把附件算成 0 字节。文件预算继续统计真实文件，最终 HTTP 请求预算统计实际 URL JSON；两种口径不同但都执行。
- API 请求快照、错误与访问日志对取件凭证脱敏，使用 no-store，避免反向代理缓存让文件删除失效。首次实现复用现有安全响应头逻辑，但为“上游下载”明确响应模式，不能沿用网页预览时把 HTML/XML 改成 text/plain 的 MIME 策略；文件保持真实 MIME、作为附件下载，保留 nosniff/CSP 等约束。
- Base64 为有界的可选传输策略。优先在发起模型请求前决定；模型请求开始后不因文件问题自动重复整次付费调用，不把模型声称没读到文件当作可靠的网络失败信号。
- 对象存储直达预签名 URL 后续可替换下载实现，减少应用中转带宽。但 S3 等直达链接在期限内通常不能按应用授权即时撤销，不能在未明确删除语义前与本站下载入口混用。

这些改动集中于附件规划、授权服务和 Chat01 编码边界；现有上传、配额、文件管理与其他渠道默认行为继续复用。首轮仅完成 Chat01 所需能力与关键边界，不同时开展所有厂商 Files API、CDN、完整预览重构或通用文件网关。

### 后续复用：官方接口的传输差异（2026-11-05 文档核验）

用户提出将其他渠道原生输入也切换到 HTTPS。本次只核验源码和官方文档，未调用 OpenAI/Google 付费 API，也未改变任何渠道配置。

- [OpenAI 文件输入](https://developers.openai.com/api/docs/guides/file-inputs)：Responses 支持 Base64、上传后的 file_id、外部 file_url；Chat Completions 文件内容仅支持 PDF 的 Base64/file_id，不支持外部文件 URL。[图片输入](https://developers.openai.com/api/docs/guides/images-vision)另有 URL 能力，不能把 PDF 的限制套到图片上。文档未要求所有输入优先用 HTTPS。
- [Gemini 输入方式](https://ai.google.dev/gemini-api/docs/file-input-methods)：外部 HTTPS/预签名 URL 已有官方支持，但单文件上限 15 MB、Gemini 2.0 系列不支持，且类型/模型范围有限。当前页面称输入方式适用于 Gemini API 各端点，URL 示例使用 Interactions；本项目 generateContent 路径仍需针对实际模型验收，不能当成已经通过实测。
- [Gemini Files API](https://ai.google.dev/gemini-api/docs/files)适用于大文件及复用，上传副本 48 小时过期。其上传容量不等于模型可处理容量；还要执行类型、页数、时长、上下文与站点预算。不能把几十 MB 音频统一改为受 15 MB 限制的外部 URL。

因此通用传输边界应能容纳三种实现：内联 Base64、外部 HTTPS、上传取得上游文件引用。管理员未来可在渠道选择“自动”或明确模式，适配器按实际接口/模型/文件类型和大小判断；前端聊天附件菜单不增加此类技术选项。强制模式不适用时发送前明确报错，自动模式也不能通过重复付费模型调用探测支持情况。现有兼容渠道维持原行为，逐条验证后启用。

Files API 后续需要独立的上游文件引用缓存与生命周期：至少按用户、原件/发送副本版本、渠道及实际凭据/项目作用域隔离，处理有效期、失效重传和远端清理；不能将一个账号的 file_id 用到另一账号。HTTP 链接和 Base64 只改变运输形式，Files API 则会在上游增加一份上传副本，不能把三者都表述为“没有额外存储”。该缓存仅优化运输，不承诺附件不占模型上下文或免输入 token。

地区核验：[OpenAI 支持地区](https://developers.openai.com/api/docs/supported-countries)与[Gemini 支持地区](https://ai.google.dev/gemini-api/docs/available-regions)均包括日本。未见普通机房 IP 一律禁止的官方规则，不能据此保证某个具体 IP/账号不受其他访问控制。模型 API 请求出站和厂商回取附件是不同方向；改变附件运输方式不应改变渠道端点或代理配置。OpenAI 的 IP allowlist、地域和额度错误有[各自错误码](https://developers.openai.com/api/docs/guides/error-codes)，与本站取件失败分别诊断。

## 混合响应：先规范化，再复用界面

保持一条助手消息的正常正文顺序，独立维护思考、工具执行记录、图片和文件产物。正常的阶段性答复和最终答复都保留，不只取最后一次 Answer。

| 实际片段 | 归属与现有展示 |
| --- | --- |
| 正常阶段性答复、最终回答 | 原有正文，保持顺序；不能因后面又有 Answer 就删除前文 |
| 思考摘要及明确的思考片段 | 原有思考展示 |
| 搜索摘要、查询或可得来源 | 原有搜索/工具过程；只展示实际收到的信息 |
| Python、Shell 执行片段及可得输出 | 原有只读工具详情；标识由本地 run 和片段顺序稳定生成 |
| 生成图片 | 复用图片展示、预览、下载组件；与正文位置关联，不把整条消息切成纯生图模式 |
| 生成文件 | 复用产物保存、正文链接和回复末尾的文件卡片 |
| 标准表格、普通 html 围栏 | 沿用 Markdown/Artifact，HTML 文件仍隔离预览 |
| 私有组件 | 数据完整且已有对应能力时转换；否则保留可读信息、可见占位/入口及原始数据，不无声删除 |

`Answer`、`Thought` 和 think 标签仅是边界证据，不直接决定全部归属。增量解码结合代码/命令结构、工具活动标记、段落上下文与后续片段，纠正错放进 Answer 的执行记录。不能把正常教学代码或用户要求的代码答案一律移入工具区。

解析器要处理分片标记、粘连标记、重复 Answer、未闭合 think/代码围栏、结束时残留文本，并保持原文可追溯。对待定片段保留小范围缓冲，避免先把代码渲染成正文再大幅搬动。流式显示与最终保存必须一致，刷新后不能变成另一种分段。

工具字段不完整不妨碍展示：已有摘要/代码/结果即可进入相应过程组件；缺查询、stdout、状态或调用 ID 时不补造，也不把这些记录交给本地工具重跑。此分流是本功能核心验收项，不以“原样放正文”作为交付结果。

## 图片、文件与私有组件

- 图片可能早于最终 Answer、也可能混在过程区。明确的最终图片接现有产物链路；若收到预览阶段或替换关系，按同一生成任务更新预览再落最终结果。当前样本没有验证过程预览协议，不能按“URL 相近”任意合并多张独立成图。
- 图片/文件下载与正文完成分别结算状态。单个 CDN 文件失败，保留其他已完成内容和可尝试的原链接；不重跑模型来重试下载。具体本地保存/外链模式需要与存储和文件卡片语义保持一致。
- URL 来源必须明确属于当前响应产物，不能把普通网页引用当文件抓取；类型检查不只依赖扩展名或 octet-stream。成功保存后沿用用户文件权限，重试与重放不重复创建文件。
- 未识别的官网组件不作为普通 HTML 直接执行。用户后续提供官网样本时，再按实际出现频率和数据完整性决定是否增加对应转换；不能先承诺覆盖所有网站私有组件。

## 自动工具、权限与长任务

本批未传工具声明仍实际出现搜索、代码、文件和生图，说明这些属于 Chat01 上游自动能力。项目自己的 MCP/函数工具权限继续独立执行；尚无证据证明本地工具开关能够逐项禁止 Chat01 的内置行为。在验证可用控制参数前，不提供名义上关闭但实际上无效的开关；需要限制某项内置能力的场景，应通过明确的渠道/模型授权或经过验证的上游控制实现。

心跳依据底层传输活动，空 content 和 SSE 注释也续活；不把 chunk id 当稳定工具 ID。Responses 已实测完整 output_text.done 快照重复发送，按响应/输出/内容索引和完成状态幂等处理，不能重复追加。上游空闲超时、任务总时长、前端连接恢复分别管理。Pro 本轮未调用，40–60 分钟场景仍需专门验收。前端连接异常误报失败与标题补偿另见 [只读排查](background-run-title-audit-20261104.md)，后续可独立修复，不要求用户提供生产日志后才处理已确认代码缺陷。

## 实施顺序与验收

1. Base64/URL/Responses 附件实测已完成，以原件 SHA-256 和回传文件校验为证据；具体覆盖范围见探测文档，不泛化成所有格式和大小已验证。
2. 独立供应商与适配器、统一通用原件输入；确认普通/临时/历史/切模型路径使用同一规则。
