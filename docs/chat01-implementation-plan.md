## 1. 交付目标

增加独立 Chat01 供应商预设及适配器，完成附件输入、混合响应分流、图片与文件产物、历史切换。上传、文件管理、授权、预算、账务、消息保存和现有展示组件继续复用。

首版默认走已经充分捕获样本的 Chat Completions。Responses 的附件 URL 输入已验证，但不为同一个供应商同时推出两套可选业务链路；解析器、附件规划和产物服务与入口协议分离，为以后增加 Responses 解码器保留边界。已有 OpenAI、Gemini 等渠道不自动迁移传输方式。

配置使用独立 adapter 身份，不通过模型名或 URL 包含某个字符串判断。模型所属厂商与渠道供应商分开；使用用户提供的 Chat01 logo。

### 1.1 管理入口与模型预设

- 上游“兼容类型”新增 Chat01，选择后默认对话协议为 `Chat Completions (Chat01)`。这是独立适配器身份，复用通用 HTTP/SSE；首版不展示尚未实现的 `Responses (Chat01)`。选 CC 的依据是当前混合响应样本更充分，不宣称它普遍优于 Responses。
- 对话内自动生图仍属于聊天返回，不据此声明支持独立 Images/Video 端点；其他既有协议不因这项适配改变。
- 从 Chat01 上游新建专用模型时，默认厂商 Chat01、展示分组跟随厂商；保留单独设置模型图标和分组的能力。已有平台模型可能被多上游共用，调整一条路由不强改其全局厂商。
- 模型输入界面采用“文本、图片、文件”，文件使用通用附件图标，能力键采用 attachment；不再为 Chat01 逐项展示 PDF/音频/视频原生勾选。实际能力必须由路由适配器及模型有效配置共同确定，厂商显示名称不能授予额外能力。
- 可直接发送的非图片文件复用绿色“原生”标签；图片不加该标签。Chat01 logo 使用用户提供素材，圆角沿用现有图标容器。

## 3. 混合响应的分类算法

### 3.1 分四步处理

1. **协议解码**：区分真正的增量、完成快照、心跳和终止信号。空 content、SSE 注释也表示传输活跃。不能把不稳定的 chunk id 当工具 ID；不能为了去重而删除内容相同的合法段落。
2. **增量扫描**：跨网络分片识别 think 标签、Answer/Thought/Python 等段落标记、代码围栏、引用、链接与私有组件边界。维护小范围未完成标记缓冲和当前块状态，不在每个 delta 上重新扫描整个回答。已捕获的粘连标记和未闭合围栏建立明确的恢复规则。
3. **按证据分类**：结构化字段优先，其次是供应商专用边界及执行标记，再结合所在段落的语法。Answer 只是候选正文边界；think 内也可能存在工具代码、执行结果和图片。教学代码与用户要求输出的代码保留在正文，不能只因出现 Python、Shell 或代码围栏就搬走。
4. **统一事件与保存**：每段具有本地 run 内稳定的 ID、顺序、来源位置、类型和解析版本。流式展示与最终保存共用这份结果；允许尚未确定的段落短暂缓冲，确有后续证据时更新同一个块。不能靠结束后另一套正则再切一次，造成刷新前后不同。

分类规则组织成小型、可独立回放的识别器及优先级，不堆成长串互相覆盖的正则，也不默认额外调用一个收费模型猜分类。解析耗时按输入长度增长，单个未闭合标记或组件有缓冲上限；超限保留为可读的未识别过程内容，不能无限等结束或吞掉后面的正文。

### 3.2 各种内容如何处理

| 返回内容 | 处理与展示 |
| --- | --- |
| 多段 Answer | 保留真实阶段性答复与最终答复的顺序，不只留第一次或最后一次。工具与思考从各段分别抽取 |
| 错放进 Answer 的思考、执行信息 | 按明确的 Thought、执行标记与上下文证据归入思考或工具过程；不凭一句“我会……”删正文 |
| 未闭合 think、代码围栏 | 根据后续已验证的段落边界结束当前解析状态；修复显示结构，不补写不存在的代码或内容 |
| 命令及代码 | 进入现有只读工具详情；代码出现于答案示例时仍留正文 |
| 命令结果 | 有真实关联 ID 就关联；没有 ID 时只在同一明确执行块且关联唯一时配对。无法确定的输出独立保留，不拼给邻近的另一条命令 |
| 不完整工具记录 | 展示实际收到的查询、代码、输出和错误；没有结果、退出码或状态就保持未知，不将流结束等同于工具成功 |
| 搜索及引用 | 已知搜索过程进入工具区；真实来源 URL 进入现有引用。只有内部 ref、无目标地址时保留可读引用信息，不伪造链接 |
| 生成图片 | 复用现有生图展示、放大及下载；同一条消息仍可包含文字、工具和文件。代码绘图也可用同一个图片展示组件，不冒称调用了生图工具 |
| 搜索配图 | 正文引用的图片直接在对应段落预览，可放大并保留真实来源；只出现在搜索过程的图片留在可展开的工具结果。默认外部引用，不自动保存到用户文件库或本站公共缓存；不按 CDN 域名认定为生图 |
| 中间预览图 | 只有明确的生成任务/阶段/替换关系才更新同一张图；未知关系不按相近 URL 合并，不将所有图片都当最终产物 |
| 生成文件 | 确认属于当前返回产物后接入文件保存及消息末尾文件卡片；网页引用不按后缀自动抓成附件 |
| 表格、普通 HTML 代码块 | 继续现有 Markdown/Artifact 行为，不能将它们称为已经支持官网原生组件 |
| 官网私有组件 | 按组件类型和载荷版本识别。信息足够且现有组件能表达时转换；否则保留标题、条目、链接等可读信息与折叠的未支持内容，不执行上游 JS |
| salt 等协议噪声 | 只过滤经样本确认的控制字段或独立控制块；不按关键词全局删文本，不删除用户代码或答案里正常出现的相同字符串 |

服务端工具过程写入 ServerToolCalls/现有 process trace 等展示通道，**不能进入本地 ToolCalls 执行队列**。模型描述“运行了命令”不构成让 DEEIX 再执行一次命令的指令。

2026-11-05 用户追加确认：复用现有代码工具详情和过程块，命令、代码、实际结果及错误各入对应位置，正文中的真正答复保留。`llm.ToolCall` 已有 ArgumentsJSON、OutputJSON、ErrorJSON、Status；Chat01 在专用适配边界填充这类共享数据，不伪造 OpenAI 的供应商身份或调用计费。有明确对应关系才合并输入输出；结果混杂且关联不明确时保留为同一过程中的有序记录，不丢弃、不强配给相邻命令。只有代码、只有结果或截断片段都能展示，缺结果不等于执行失败。回放不再给所有代码块统一挂“未返回独立执行结果”的说明。

已捕获的 map_widget_v2 只有地点内部引用和部分卡片信息，没有可还原地图的坐标载荷。因此首版能保留地点与可用链接，不能承诺重建官网交互地图。完全没有结构标记、与正常答复语气相同的自然语言也不能保证百分之百分辨；不以猜测删除内容。异常原始片段保留在受权限及大小限制的诊断记录中，便于补规则，不能无限复制整个回复到每个事件。

本轮的交付标准是已捕获复杂样本全部按审核后的期望分段通过，包括多段正文、内联 think、未闭合代码、混合图片和文件，而非把难以识别的整份响应原样塞回正文。

2026-11-05 已交付 [分类回放实验](../scripts/experiments/chat01-response-replay/README.md)，并增加 [复杂任务实测](chat01-response-stress-20261105.md)。累计十份抓包通过原始内容保全、真实 SSE/逐字符等分片一致性与正文代码保护检查；另有十二个合成边界检查。已修正粘连标记、截断代码、残缺加粗标题吞正文和代码字面量误分流。未提供独立调用结果的执行片段仍标为片段，不凭任务要求或最终自述推断完整工具次数。这些检查证明已覆盖样本的边界行为，不等于对任意自然语言完成语义判定。后续修正规则留在解析核心，避免散落到展示层。

正常正文增量输出，不等待完整回答；仅潜在标记和未完成组件有界暂存，组件需要完整结构后再挂载。图片/产物获取独立推进，不阻塞后续正文。解析缓冲不得阻止网络心跳处理，也不以界面暂时未出字判断上游断流。

### 3.3 Chat01 强制禁用 DEEIX 提示词驱动组件（用户已确认）

2026-11-05 用户明确要求：Chat01 隐藏且强制关闭 DEEIX 原生对话组件入口，不注入相关提示词，不允许沿用从其他渠道带来的开启状态。这一限制针对 DEEIX 的输出格式引导，不禁止识别 Chat01 自己返回的组件。

源码核对：`use-chat-ui-components.ts` 将选择保存为跨会话的设备偏好，未显式选择时采用启用的内置组件；`system_prompt.go` 分别注入组件目录和 HTML Visual 格式提示，后者并不由清空目录自动关闭；`ui_state_context.go` 另行收集组件交互状态。普通与临时会话均涉及这些路径。

实施使用同一个已解析渠道能力判定，统一覆盖：

- 前端隐藏组件选择器及其 HTML Visual 开关，本轮有效组件选择为空，不收集 DEEIX 专用状态回传。
- 后端在实际路由确定后强制禁用组件目录、HTML Visual 格式提示及 DEEIX 专用状态注入；直接构造请求、旧客户端、重试或故障转移都不能绕过。
- 不删除用户对其他渠道的设备偏好；切回支持渠道时恢复其原有选择。历史消息和已生成组件不因切渠道而从界面消失。
- 保留平台、模型、项目的正常指令；不把“关闭组件格式提示”扩展为取消所有系统提示词。
- 输出渲染与输入格式引导分离。Chat01 组件只有经适配器识别并规范化的载荷才能映射到共享组件；不能仅因上游文本出现 `deeix-ui` / `deeix-widget` 围栏就宣称已验证官网组件来源。
- 对已支持的 Chat01 交互动作，复用通用交互分发。官网已核对的 prompt 回调实际填入输入框，首版沿用该语义，由用户正常发送；已有草稿不得静默覆盖，本地控件状态变化不产生模型请求。发送继续检查会话、权限、附件和预算。不开启 DEEIX 提示词注入，也不把上游任意回调、JS 或内部接口请求直接执行。需要官网私有会话状态而 API 未提供的动作明确保留为未支持。

用户提供 [地图样本](https://chat01.ai/zh/chat/01M68PFTXY1K45CN5SQN25AH8Y) 和 [组件枚举样本](https://chat01.ai/zh/chat/01M6N21DQNFD23HH0A8D47WXYZ)。浏览器和 Computer Use 已实际调用，但浏览器发现与网址识别仍失败，未取得登录态页面。用户随后将组件枚举页公开，现已通过 HTTP 读取该页 HTML、消息数据及两段完整 `chat-ui:v1`；包含实际地图坐标、DIL 代码、专用 widget 和图片/引用/后续问题的解析数据，未执行交互。公开前端脚本也确认了解码、节点注册表和隔离运行时，详见 [核对记录](chat01-widget-protocol-audit-20261105.md)。

基础控件与数据组件采用注册表适配；需要完整 `runtime.widgets`、`appData` 或坐标的内容，不能凭内部 ID 补造。官网两段样本的 `nodes` 都为空，小游戏依赖动态代码，无法仅靠声明式节点映射完整复现。现有 API 文本捕获只见 `map_widget_v2`，未见官网这种完整尾部协议；下一步差距是确认 API 是否提供完整载荷。首版不移植整套 DIL/应用执行运行时，缺失数据保留可读内容与局部未支持状态。地图载荷已发现地址与坐标不一致，交互代码也有调用未见实现接口的情况；不把模型自述当可用性保证，不自行补造上游数据。

新增组件专项请求仍未返回完整 `chat-ui:v1`：地图只有地点 ref；排序表格只有表头；计数器、后续问题没有回调或状态。搜索图片仅给出了 Wikimedia 网页链接，未给图片地址。以上可保留已收到的文字、地点和来源，不能伪造可点击按钮、地图坐标或把网页 URL 作为图片地址。此结果只描述已测请求，不宣称该 API 永远不返回完整组件。

### 3.4 提示词与功能边界（按最新用户说明拟定）

Chat01 接受 system 字段；按用户说明，上游把它拼成官网会话的前置消息。适配不擅自把它标成“不支持 system”，也不靠增加长篇提示词控制上游 Agent。普通指令依既有优先级和授权发送；减少的是无用格式说明、不可执行的本地工具说明及重复上下文。约 70k–100k 是用户提供的运营经验，不冒称厂商精确窗口或固定 token 统计。

| 来源 / 功能 | Chat01 首版行为 | 原因 |
| --- | --- | --- |
| 平台、模型、项目的已配置指令 | 保留，不自动添通用角色、语言或格式要求 | 这是管理员和用户明确配置的功能，不能按 system 角色整批删除 |
| 用户选择的 Skill | 保留所选 SKILL.md 和必要身份信息；不加载未选技能目录 | 写作规则、分析流程、输出要求仍有价值；加载技能不等于额外授予本站工具或文件 |
| Skill 默认包装说明 | 按实际能力使用简短版本，不带“只可调用本站显式提供工具”的默认禁令 | 现有默认禁令会干扰官网自带搜索、代码与生图；自定义 Skill 内容和管理员自定义说明不靠正则改写 |
| Skill 引用的本站 MCP、脚本和本地文件 | 不假装可用，不自动执行或上传；未来若支持包含脚本/资源包的技能，Chat01 禁用此类技能，本轮不增加脚本传输 | 当前 Skill 只有 Markdown 文本，没有随附脚本或依赖声明；代码示例不等于脚本包，不能按关键词误禁现有文本技能 |
| MCP / 本地函数工具 | 用户已确认禁用：隐藏选择入口，不发送 definitions、使用指导，不创建执行循环 | 上游服务端 Agent 工具继续工作；它们与 DEEIX 的工具执行队列不同。依据当前接入边界禁用，不宣称“流式 API 天生不能调 MCP” |
| DEEIX 交互组件 / HTML Visual | 按上一节强制关闭提示词和专用状态注入 | 上游返回的真实组件和普通可预览内容另行识别 |
| 记忆 | 用户开启记忆时保留既有短偏好，沿用约 400 tokens 的现有上限；Chat01 默认不做 profile/custom 的额外召回及广泛语义召回 | 保留语言、表达习惯等少量有效信息，把更多上下文留给任务；关闭记忆的用户仍不注入 |
| 附件、明确选择的知识库 / 检索 | 保留实际选择的任务材料；原件与同文件解析文本不重复注入 | 这是任务数据，不能随工具说明一起删掉；本站完成的检索不要求模型调用 MCP |
| 分支摘要与必要文件状态 | 保留维持当前对话所需的内容；不自动再摘要一遍来省 token | 它们属于有效历史，删除会失去任务信息；原有压缩策略另受用户配置控制 |
| 标题、标签等元数据任务 | 与主对话提示词分开，继续现有独立任务 | 不向主对话追加标题生成要求；标题补偿 bug 另排在 Chat01 之后 |

封装位置：在应用层按最终解析出的路由能力产生一份有效提示词策略，传给公共 prompt planner 与工具解析入口。按来源决定哪些输入有效，再序列化；不能等 system 文本合并后用正则删除。普通、临时、重试和故障转移共用；切到其他渠道重新计算，不篡改其原有偏好。后台权限、文件归属和计费仍由服务端执行，不依赖 system 约束。

实现接点：`route_policy.go` 按实际路由提供有效策略；`system_prompt.go` 合并平台/模型/项目及组件说明；`prompt_plan.go` 注入动态上下文、Skill 和 MCP 指导；`service_skill_prompt.go` 解析选中技能，Chat01 使用精简默认包装；`service_message_send.go` 保留短偏好、排除广泛记忆召回。普通、临时及路由重试已接入。

补充核实：`domain/skill/types.go:12–27` 和 `transport/http/skill/dto.go:48–65` 只有 Markdown 内容及管理元数据，没有脚本附件、资源包或执行器入口。现有技能继续作为文本使用；用户在 Markdown 里写代码不视为可执行资源。

知识库由本站检索，再把命中的相关片段交给 Chat01，不要求上游有 MCP 或原生 RAG 接口，也不把整个知识库塞进请求。选择阶段仅验证权限、存在性与检索可用性；实际检索量依问题而变，完整上下文统一在发送前判断。默认启用的 contextBudgetPolicy 在普通与临时会话组装完文件、RAG、Skill 等内容后执行；超限时沿既有报错和草稿保留逻辑，已启用自动压缩则按现有策略重建后复检，不为 Chat01 静默截断知识片段。依据 `service_message_route_attempt.go:74–176`、`service_message_send.go:714–785`、`service_temporary_chat.go:157–195`。模型能力配置中的实际窗口仍由管理员管理，70k–100k 经验值不意味着本站能突破上游未公开的真实上限。

## 4. 附件与 HTTPS

### 4.1 能力和限制

Chat01 有效能力展示为“文本、图片、文件”。非图片不要求逐项勾 PDF、音频或视频；分类仍保留，用于图标、预览、上传规则及切到其他模型后的判断。Chat01 选原件时不等解析、不重复注入同一文件的解析全文或 RAG，后台解析沿用现有设置。

| 项目 | 首版规则 |
| --- | --- |
| 上传入口 | 继续现有白名单、分类上限与用户空间规则；Chat01 能接收不代表上传限制自动放宽 |
| 单附件 | 用户已确认的 Chat01 运营上限 100 MiB，仍受适用的更小限制约束 |
| 整次请求附件合计 | 图片实际发送副本与其他原件合计 100 MiB，包含实际携带的历史附件；不能借 URL 很短绕过 |
| 单条消息附件数 | 沿用已有配置，不偷换成完整历史数量 |
| 完整请求混合附件数 | 建议为 Chat01 新建渠道预设 10 个，作为保守运营默认值，通过现有预算管理入口配置。10×10 MiB 已验证，不宣称这是厂商硬上限 |
| 图片及原生分类预算 | 图片处理后大小、图片数等已有更细限制仍生效；混合总量规则不替代它们 |
| 最终请求体 | 统计真实 JSON；HTTPS 时通常很小，Base64 则计算编码后的膨胀与其他内容 |

混合数量/字节是通用预算指标，仅在有需要的渠道启用；不再增加一套 Chat01 管理页面。发送前使用最终实际渠道的有效配置。URL 重复 GET 不重复计入附件数量和内容预算，但会产生实际出站流量。

HTTPS 只减少传输请求体，不取消附件预算。PDF、音视频仍沿用原有保守 token 估算；通用文件是官网 Agent 工作区附件，只估文件清单元数据及真正注入的文本，不把 ZIP/Office 二进制按 PDF 每页字节折算成上百万 token。上游自行读取文件后的内部上下文不可观测，缺少 usage 时不编造精确值。渠道路由或故障转移若选择了不同适配器，必须重新规划和检查附件，不能直接转发上一渠道的已序列化请求。

### 4.2 授权链接

- 复用已有 HTTPS 反向代理及 PublicAPIBaseURL，不需要临时隧道、另建证书或公开存储目录。模型在 file_url/image_url 字段收到链接，不把链接或取件凭证写进用户提示词。
- 通用授权服务使用现有 Redis/memory 装配，保存少量授权元数据和随机凭证摘要，限定用户、文件版本/发送副本、本轮任务、用途和期限。每次读取重新检查文件有效性，不能把一次性 OAuth grant 或会话分享链接当附件取件权限。
- GET、HEAD 在有效期内可以多次调用，覆盖上游重取；浏览器离开不撤销仍运行的后端任务。时效按后端任务允许时长加有限宽限期设置，结束/取消/异常有回收和到期兜底。
- 每轮重新签发，历史保存文件 ID 和版本，不保存临时授权 URL。删除后拒绝新的取件；已送出的字节不能收回。
- 真正流式读取，固定缓冲、有界并发、取消与错误处理。若存储支持高效 Range 可复用；不为 Range 将整个文件加载进内存。响应不缓存，日志脱敏，真实 MIME 与下载文件名保留。
- 图片 URL 指向本轮处理后的版本；有界复用该版本避免每次重取重新缩图，不以 HTTPS 为名发回未处理原图。未来浏览器预处理后上传可以直接提供这一版本。

链接持有者在有效期内可读取指定文件；限定用途不是对 Chat01 的身份认证。其他文件不因此公开。日后对象存储预签名实现需要单独处理删除/撤销语义，不假定与本站鉴权接口完全相同。

### 4.3 Base64 回退时机

首版采用自动选择：配置可用 HTTPS PublicAPIBaseURL 时优先签发链接，没有该配置时在预算允许范围内用 Base64；不增加聊天附件菜单或新的传输设置面板。显式选择 HTTPS/Base64 的管理选项保留为后续扩展。选择发生在付费模型请求前，签发失败、删除或失权不走绕过校验的回退。

模型请求发出后，不因断流、附件准备失败或自然语言称“没看到文件”而自动再发一次 Base64 请求。这样无法保证不重复计费。授权失败、文件已删、预算超限也不能用回退绕过。100 MiB Base64 的既有探测为 413，故大文件不能保证有内联备选。

## 5. 切换模型与渠道

附件持久化一次，HTTPS/Base64 是本轮传输选择。每次发送依据当前分支、实际模型和渠道重新规划，不能将 Chat01 的广泛附件能力固定在文件记录上。

| 场景 | 行为 |
| --- | --- |
| Chat01 → 支持该类型原生输入的模型 | 用同一源文件重新准备目标所需的输入；URL 不支持时可采用该渠道原有内联链路 |
| Chat01 DOCX/PPTX → 无原件能力但有解析途径的模型 | 复用已完成解析；仍在解析则显示现有处理状态；需要启动解析则沿用该链路；不把原件当已经读过 |
| Chat01 音频/其他文件 → 既无原生能力也无解析途径的模型 | 阻止发送，明确指出文件及能力问题；不静默忽略历史附件 |
| 其他渠道 → Chat01 | 从文件记录取原件/图片发送版本，重新校验限制并签发链接；不只发此前提取出来的文字 |
| 切走后再切回 Chat01 | 重新计算为原件路径，不重复上传；解析结果可以保留，但不与原件重复注入 |
| 目标渠道更小的数量/大小限制 | 以目标渠道生效值报错，不裁掉旧附件凑数 |
| 历史文件已删除或失权 | 明确报错并保留当前草稿；不偷偷恢复文件，也不假装还带着附件 |

切换本身更新附件状态与能力提示，不每切一次就弹窗；发送前统一检查本轮及实际历史附件，后端最终校验兜底。采用项目现有错误及草稿保留机制，普通和临时会话一致。

**展示历史与再次发送的上下文分开**：正文中真实的阶段性答复及最终回答可进入目标协议；Chat01 的思考和服务端工具日志保留供用户查看，不伪装成目标渠道的 reasoning/tool_call 协议。源沙箱、容器状态不会随切渠道迁移，也不承诺在 Chat01 内跨请求沿用同一个沙箱。

已保存的生成文件可供用户下载、预览或按现有入口选为下一轮附件。不能把一轮所有生成产物无条件自动重新挂入每次模型请求，悄悄耗尽 10 个附件预算。正文里的文件链接是资源引用，不等于目标模型已收到原件。上下文观测/缓存标识使用稳定的源文件版本和处理参数，不能因每轮 URL 随机凭证变化而全部失效。

## 6. 生图和生成文件的交付

明确生成的图片、代码绘图和下载文件默认保存到本站，成功后进入现有用户文件管理、权限及存储统计，正文链接替换为项目受保护的资源地址，回复末尾直接接现有文件卡片，不增加“回复中的文件”等标题。图片复用现有图片展示，按产物身份处理正文引用与附加展示，避免同一资源重复落盘或因回放重复建卡。搜索配图、外部参考图片及来源不确定的图片按下述外部引用政策处理，不因为同属图片而自动导入。

解析器只产出带来源证据的资源描述，由独立来源读取器获取。只有明确属于本次响应的下载/图片来源才导入；网页来源仍走引用。下载使用已验证 CDN 来源范围、重定向与实际内容检查，不把 Chat01 API 密钥发给 CDN，不接受任意内网地址作为产物。

- 正文完成与产物保存状态分开，单个链接失效不能删掉其他文件或使整段回答消失。
- 每个产物独立报告保存成功/失败。失败项保留原链接和失败状态，不能伪造文件 ID 或显示为已入库。
- API 实测仍可能残留 `sandbox:/mnt/data/...`，且没有容器标识或可下载映射。按用户确认，此类地址显示链接文字或文件名及“（上游返回的下载地址无效）”，不保留可点击的伪下载入口，不套 OpenAI 容器 API 或猜 CDN 地址；同轮其他可用产物照常处理。仅在 Chat01 产物缺少有效映射时适用，其他渠道有明确容器引用的正常下载链路不受影响。
- 对仍可访问的原链接可提供外部下载入口；“重试保存”只重新下载这个产物，不再次调用模型。链接已过期则如实提示，不能承诺能够恢复。
- 落盘和重试按本轮来源身份幂等；相同字节用现有存储去重，不凭文件名或 URL 相似度合并不同产物。
- 复用现有模型产物单文件上限与用户空间事务。核实当前 SQL 的实际行为仍为严格配额，过去讨论的“一次超额保留”尚未实现；本轮不暗中绕过配额。保存失败时保留可用 CDN 链接及失败说明，不使其他成功文件回滚。统一的超额保留机制需要独立补齐，不能在 Chat01 每个文件上分别豁免。
- 现有生成文件保存存在批次失败回滚路径；Chat01 所需的逐项结果封装在共享产物服务边界，保留旧调用兼容包装，不让一条失效 CDN 链接抹掉已成功产物。

本轮沿用现有预览。右侧文件预览、PDF 缩略页、DOCX/PPTX 新预览、HTML 产物与 Artifact 统一布局均后置。可信文件记录和统一资源身份建立后，这些展示可以独立迭代。

### 6.1 搜索图片的归属与迁移（用户已确认外部预览）

- 默认通过现有 MarkdownImage/image-gallery 展示外部图片，浏览器按需加载；消息保存资源链接、来源和说明。现有 MarkdownImage 已有外部图片预览/放大/下载，不需要先创建用户文件才能展示。
- 不建立无限增长的公共图片存储，不自动占用户空间，也不为搜索配图新设本站“30天删除”规则。浏览器自己的缓存不属于本站持久化文件。
- 外部来源可能撤回图片或让链接过期，此时复用图片加载失败状态并保留出处，不声称外链永久有效。首版不为规避外链失效而默默启用无界服务器缓存。
- 下载到用户设备不等于保存到本站。用户明确保存为站内文件、或后续作为附件上传时，才走现有文件归属、空间额度、去重及删除规则。单独“保存到我的文件”入口如有必要另行审核，不为本轮增设一套图库。
- 服务器迁移沿用数据库、现有文件存储和必要配置/密钥的迁移流程。外部图片引用随消息数据库迁移；已保存文件随现有存储迁移。内部资源使用稳定文件 ID/存储键，临时 HTTPS 授权链接按新站配置重签，不把旧服务器域名或临时凭证作为文件身份。

## 7. 权限、计费和长任务

渠道/模型使用权限、用户与团队限制、预算预留、扣费和账单记录继续走现有路径。Chat01 已观察到无需声明便自动搜索、执行代码和生图，所以这些过程属于上游服务，不伪造可逐项禁用的本地工具开关。若某类用户必须禁止上游执行代码等行为，在未验证上游有真实关闭能力前，不应向该类用户授权此渠道。Chat01 的 MCP/本地工具按有效能力强制关闭，其他渠道的授权和配置不变。

项目已有模型按次计费，建议 Chat01 首版采用该模式，由管理员设本站价格；不把探测时的上游分数直接当本站价格。不返回可靠 usage 时不伪造精确 token；代码/搜索过程规范化不会凭空增加 OpenAI 原生工具账单。失败、取消、重试仍按现有账务规则处理，必须将真实终态传进去，不宣称所有失败都免费。

心跳、读空闲超时、任务总时限、前端连接状态分别管理。依渠道设置支持长任务，所有实际传输活动都维持读取活跃；无活动才触发读空闲规则。HTTP 200、[DONE] 不足以认定成功，已捕获的整段 Attachment preparation failed 错误需转换为业务失败，正文引用相同句子不能误判。

现有实现中，连接超时限制建连；读取超时用于非流式整次请求、流式开始取得响应；流超时是响应 body 无字节到达的空闲上限。配置 7,200,000 ms 表示两小时，流持续有心跳可以超过该时长。Chat01 适配沿用这些配置，不将用户已设的大值悄悄改小；连接等待建议与长生成时间分开配置。当前已核对的路由传参和 HTTP 读取路径没有以熔断开关门控这些超时，页面“仅自动熔断开启后生效”不能当作已经验证的运行规则。部署代理和后台任务时限另行核验，不用新解析器替代连接生命周期管理。

用户补充 Pro 最长约两小时，首版新建 Chat01 预设连接 30,000 ms、读取及流空闲 9,000,000 ms（150 分钟）；已有自定义设置保留。HTTPS 授权默认及最大期限为三小时，结束/取消时撤销，前端离开不影响后台任务。生成文件下载独立限制为总计 120 秒、无数据进展 30 秒，不能沿用推理的 150 分钟等待。测试覆盖心跳、取消、过期及可重复取件，未付费调用 Pro，也未将其等同于真实两小时端到端验证。

重复快照/重连回放不能重复追加内容、存文件或扣费。浏览器切后台不自行把后台运行状态改成失败；复用任务恢复机制。既有标题生成补偿与通用误超时问题继续独立排期，本轮只修阻断 Chat01 正确运行的必需集成点。

2026-11-05 复核：通用标题/误超时问题尚未修复；标题后台任务仍单独限时 90 秒，失败后没有重试补偿，前端发送异常仍可能先标失败再由后台恢复。相关源码证据见 [既有审计](background-run-title-audit-20261104.md)。按用户要求在 Chat01 完成后处理，不把当前计划当成修复已落地。

## 8. 性能、持久化与升级

- HTTPS 通道不持有 100 MiB 文件的多份内存副本；限制并发取件/产物保存，复用连接、流式传输和取消信号。不会为了自检每个 URL 再完整下载一遍。
- 记录文件请求起止、状态和已写字节，区分本站写出与上游确认接收；不宣称临时隧道测试的六分钟等于生产耗时。原实验的约 60 秒中断尚不能定位到 Chat01、隧道或网络，未发现测试脚本的 60 秒重试定时器；正式取件复用项目 Go 文件服务。
- 共享接口变化控制在文件引用、预算取值、标准响应事件和产物来源读取边界。Chat01 语法规则及适配测试集中在专用模块，不在每个页面和供应商中散落条件分支。
- 计划复用现有 Content、ReasoningContent、process trace/PayloadJSON、附件关联及工具详情；必要新增字段为可选且带版本的 JSON，不增加或改写业务 SQL 表，不批量重写旧消息。
- 实施时检验消息回放、临时会话、分支及旧数据读取。未改 SQL 不等于旧镜像懂 Chat01：回滚前关闭该渠道并处理在途任务；旧版保留通用正文和已保存文件，但不承诺继续调用新适配器或识别新过程块。

## 9. 开发与验收顺序
