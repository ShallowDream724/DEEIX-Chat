# 对话输入与超限处理：统一方案（讨论稿）

更新：2026-11-04。本页记录当前代码核验、已确认方向和待讨论方案，不表示下述目标行为已上线。当前系统默认仅完整请求体为 100 MB，其他输入预算默认值尚待落地。

## 已确认方向

- 首次输入没有实测依据时接受保守估算。
- 关闭自动压缩时，达到有效上下文预算应停止本次发送，引导新建对话或修改当前输入；不通过移除旧历史来继续请求，也不把明确的本地超限交给上游碰运气。
- 普通与临时会话共享计量、预算判断和错误语义。临时会话不持久化聊天记录，不构成缺少校准或另写一套判断的理由。
- 限额提示复用 DEEIX 现有弹窗、按钮、排版、主题与国际化；按具体原因提供可操作建议。实施后以真实组件页面展示桌面及窄屏效果。
- 图片转文字摘要与上下文用量环形组件、压缩优化一起讨论，本轮不默认执行。
- 存储不足必须独立提示，不能与模型输入数量或大小混淆。切到更低数量预算的渠道后按新渠道拒绝超限发送，保留已有文件和对话。
- 当前有效上下文需要的附件若既不能原生提供，也没有允许且可用的解析路径，必须拒绝；包括历史附件。当前不提供“忽略此文件继续”入口。
- 解析后的完整内容超出适用上限时不截取一部分冒充完整输入，不静默遗漏文件；已明确采用 RAG 的路径按检索语义处理。

## 现状：哪些限制在哪里触发

| 限制 | 当前检查时机与行为 |
| --- | --- |
| 上传原件大小、类型 | 普通聊天选择/拖入后，前端已有策略时即检查；服务端读取上传流、检测类型时再次校验。分类大小覆盖默认大小，未填写则继承。上传时不依赖稍后的图片缩放来放行原件 |
| 单条消息附件数量 | 添加附件时检查；超出可用名额的部分不加入，并提示。后端发送入口再次校验，与历史图片数量不是同一项 |
| 用户累计存储额度 | 普通上传持久化时检查；不足则上传失败并清理本次未入库对象。临时附件的临时处理保护与持久存储额度分开 |
| 图片数量、处理后单图/合计大小 | 点击发送后，准备真实图片副本和历史上下文时检查；上游调用前再次校验。统计实际携带的图片，包含历史图片；不删除文件管理中的原件 |
| 原生文件数量/合计、单 PDF/合计大小、PDF 合计页数、原生音视频合计大小 | 上传后原生就绪预检及发送准备阶段检查；最终请求再次校验。现有预检主要决定原生可用标签，并非完整的超限弹窗 |
| 原生预算不足的处理 | 当前优先选择较新附件；PDF 可能采用可用的解析/RAG 内容，旧文件也可能被排除。本轮无可用路径的音视频等才拒绝。不能把现状描述为所有原生超限都严格拒绝 |
| 解析后全文大小、token、PDF 页数 | 解析结果产生后、选择全文/RAG 路径时检查；合适且已配置的 RAG 可继续使用。它不是上传原件大小，也不是原生 PDF 预算 |
| 完整请求体大小 | 编码为 JSON 或 multipart 后、发往上游之前检查；含 Base64、文字、工具定义、历史等开销，不能只相加文件大小 |
| 上下文 token | 普通和临时发送前均有预算拟合，但当前会裁旧历史；必需内容仍超预算只记日志，仍可发送。普通会话已接实测校准，临时会话尚未接入 |
| 临时请求保护 | 服务端另限最多 100 条消息、合计 100 万字符、请求元数据大小及临时附件总数；前端超过 99 条历史会先裁剪并提示。需要与新的停止发送规则协调 |
| 供应商约束 | 已知且适用的大小、数量、页面/尺寸规则在本地校验；实际模型支持、供应商额外规则及计数差异仍可能由上游返回错误 |
| 代理/服务请求体保护 | HTTP 入口和部署代理可以比业务限额更早拒绝请求。应用可检查自己的入口，不能保证收到被外部代理直接拦下的请求 |

金额、权限、并发等维持独立校验，不能把余额不足或无权限包装成上下文超限。生成文件保存限制属于输出链路，也不混入输入预算。

## 目标处理流程

1. 添加附件时检查已知的原件大小、类型和本条消息附件数，尽早反馈；未上传成功的文件不进入可发送状态。
2. 发送前按真实路由、当前分支和使用方式准备完整输入，包含历史媒体、工具和系统内容。复用原生/解析/RAG 能力判断与图片处理缓存。
3. 从可信观测校准 token，检查数量、字节、页数和上下文。能明确判定超限时停止，不执行付费的主模型请求。前端预检用于及时反馈，后端对实际请求负责。
4. 自动压缩关闭：上下文超限停止。自动压缩开启：建议只在可压缩的历史导致 token 超限时压缩并重新检查；当前轮本身超限、图片数或文件字节超限不能靠纯文字摘要掩盖。压缩失败或仍超限时停止，不循环尝试。
5. 最终编码后再次检查整个请求体；工具续问、重试和路由切换仍使用相同判断。已有工具调用发生后才触发后续限额，应保留已完成输出，结算已发生的用量，不声称整轮从未调用。

发送失败保留草稿和当前附件。删除旧历史、从文件管理中删除原件和仅从本次草稿移除附件是三个不同动作，不自动互相替代。

## 核心封装

复用现有 `shared/inputlimits`、模型能力解析、请求组装、观测算法、错误结构和 UI 原语，收拢分散的调用位置；不创建另一套设置或复制完整的普通会话服务。

- **输入与计量**：对组装后的输入计算实际媒体用量，并采用同一套“匹配实测输入 + 内容变化估算”逻辑。实测是整次输入，账单累计与当前上下文分开。
- **预算决策**：统一输出可发送、需要压缩、必须停止以及具体限制原因；编排层执行结果，工具续问复用同一决策。
- **观测状态适配**：普通会话沿用当前分支的持久化观测；临时会话建议使用受限、带过期的服务端缓存，仅保存指纹和计数。按认证用户与临时会话隔离，重试/编辑不能复用不相容的观测，不接受浏览器自行声明的 token 数为依据。缓存缺失则回退估算，不影响正确性。
- **错误与界面**：普通请求、流式事件和临时请求采用同一错误说明。前端依据稳定原因显示文案，不解析供应商自由文本、不展示内部字段名。数量、大小显示实际值；token 标明估算性质。

临时会话保留临时历史、断开即取消等生命周期语义。统一计量与预算不意味着本轮顺带增加其尚未具备的自动摘要、持久历史或断线续传功能。

## 超限后的产品行为建议

| 情况 | 建议操作 |
| --- | --- |
| 历史积累导致上下文/图片数超限 | 新建对话；可返回当前对话。迁移草稿不自动携带旧历史，不自动发送 |
| 当前这条消息本身过长 | 精简内容、移除部分附件；不能只提示新建对话，因为换对话仍会失败 |
| 本轮新增图片使数量超限 | 移除本轮图片，或在新对话继续；历史图片不能在输入框假装可直接移除 |
| 单文件过大 | 指出文件和有效上限，建议缩小或拆分；不要求清理存储空间来解决单文件上限 |
| 多附件总大小/页数超限 | 减少本轮附件；若主要来自历史，则新建对话。原生超限不能静默丢文件或擅自改变视觉输入语义 |
| 用户空间不足 | 打开文件管理清理空间；新建对话不会增加存储额度 |
| 模型不支持且没有已配置的解析路径 | 移除附件或切换支持的模型；不把类型不支持说成文件过大 |
| 全文不适合，但已配置的解析/RAG 可用 | 按明确的文件使用策略走现有路径；与原生额度超限后的自动降级是否允许分开决定 |

上传就能确定的普通文件错误沿用局部提示；需要用户决定新建对话、修改输入等发送阻断场景使用统一弹窗。多个已知原因合并呈现，避免连弹多个窗口。未知大小、缺页数、文件不可读与已确认超限使用不同说明。

## 切换模型、确认发送与草稿

- 切换模型允许完成，不自动退回旧模型。已知问题在附件/输入区域立即给出简短提示，不每次切换都弹模态窗口；异步预检返回前不把未知状态说成确定失败，忽略旧模型的迟到结果。
- 原生可用立即可发；不支持原生但解析结果已可用时按合法解析路径继续；解析中沿用现有处理状态，不报失败。完全无处理路径、明确超限时提示不可发送原因。
- 发送操作保留可触达的解释入口；点击后若已知不能发送，则展示统一原因与恢复操作，实际不提交生成请求。不要只留下无法解释的灰色按钮。最终路由确定后仍由后端检查真实输入。
- 已知拦截发生在清空草稿之前，文字和附件原样留在输入框，与“发送失败后自动恢复草稿”开关无关。提交后出现的错误复用统一恢复流程，尊重原有自动恢复设置及会话/分支归属，不覆盖用户后来输入的新草稿。
- 当前普通会话确有 `restoreDraftOnFailure` 设置（默认开启）及分支可见性判断；临时会话错误路径只更新失败消息，没有同样的输入框恢复流程。两入口需共享恢复契约，不能假定现状已一致。

## 2026-11-04 追加：预算一致性与存储核验

- 普通上传已有独立 `quota.exceeded` 错误（HTTP 409），图片/请求过大走 `file.too_large`（HTTP 413）；前端按错误码取不同文案。普通上传会在相同用户的有效文件中按内容哈希和大小复用，不重复占用一份额度。发送失败/渠道不支持不会自动删除已保存的文件。
- 全局图片数 20、当前渠道 10、有效上下文已有 17 张时，按 10 张判断；模型切换后尽早告知，发送后端依最终路由复核。不能为继续发送自动取最新 10 张。渠道配置覆盖系统值；供应商真实约束仍另行生效。
- Chat01 所谓“10 个附件”尚需核对 API 的准确口径：是每条消息还是整个请求，以及是否图片/PDF/音视频混合计数。若是混合总数，不能靠图片上限 10 和原生文件上限 10 两项代替；未来渠道适配复用公共计量并增加相应的组合约束，不硬编码到聊天前端。
- 建议原生数量/字节预算与图片采取一致的停止规则：容量不足不改变原件视觉输入语义，不排除较旧文件继续。模型不支持原生 PDF、但已允许且具备完整解析/RAG 路径，与音视频完全无处理路径需要区分。
- 当前全文注入源码默认为单文件提取文字 2 MB、65,536 tokens、单 PDF 20 页。补充核验纠正：页数不仅控制全文资格，还被临时附件和 embedding 回退提取传给解析器，内置 PDF 提取只取前 N 页但仍返回完整页数；普通后台首次提取传 0，不受这一配置截页。不能把它描述为纯粹的全文门槛。关闭全文限制开关时三值均归零。需要拆开全文预算和解析器读取保护，禁止把部分提取伪装成完整文档。
- 建议新安装全文默认保留 2 MB，token 提高为 256K；已保存的 272K 等配置不被默认值覆盖。2 MB 的 UTF-8 文本大约容纳 66 万个常见汉字或 200 万个 ASCII 字符，token 无固定换算。建议取消全文路径的 PDF 页数门槛，按实际提取文本和模型总上下文判断；原生 PDF 页数预算仍单独保留。兼容旧配置及解除两处解析器传参必须一起规划，不能仅修改前端字段。
- 当前 Gemini 内嵌发送对图片/PDF/音视频均做 Base64：编码长度为 `4 × ceil(原始字节数 / 3)`。90 MB 原件变为 120 MB，再加 JSON、文字和工具，100 MB 请求体在首轮就不足。缩放图片后的字节参与同样计算；音频目前不会自动变小。文件引用链路与上传上限、输入原件预算、编码请求上限分别判断。
- 建议完整请求默认仍为 100 MB，原生文件合计 50 MB，图片合计由先前候选 25 MB 调整为 20 MB：两类原件合计最多 70 MB，Base64 约 93.3 MB，留约 6.7 MB 给文字、工具和结构。最终请求仍需精确校验，不承诺所有文本/工具组合都能同时满载。图片数 20、单图 5 MB、原生数 10、PDF 单份/合计 50 MB、PDF 合计 200 页、原生音视频合计 50 MB仍为待落地的保守候选。
- 需要 90/100 MB 原生音频的渠道，应核对并调整原生合计和音视频合计，结合实际请求体上限或新增上传后引用的传输能力；不能只调大音频一个字段。

## 后续：编辑历史消息时调整附件

- 编辑已有用户消息时允许增删或替换附件，重新计算受影响分支的输入、校准观测和限额。以现有分支编辑语义处理后续消息，不改变其他分支。
- 从消息中移除附件只解除该消息引用，不等于从用户文件管理中删除原件；是否删除原件继续使用独立文件管理行为。此项为后续排期，本轮不增加“忽略文件继续”按钮。

## 本轮讨论需要收敛的边界

- 关闭自动压缩后的明确停止已确认；开启自动压缩时的预检、失败处理和图片摘要仍需分别讨论，不能声称文字压缩会减少图片数量。
- 建议原生预算超限默认停止；仅在已明确选择/开启解析回退的路径中继续解析。需同步原生标签、回退设置和处理记录，避免标签与实际请求不一致。
- 临时会话条数、字符、元数据保护保留为资源边界，但移除自动裁旧历史的继续发送行为，改为准确提示；是否合并或调整这些保护值需按实际用途确认。
- 输入默认值按已讨论的保守方向统一设置，渠道可覆盖；输出保存上限、单轮存储上限和一次超额度接收单列实施，不能仅调大单文件值就宣称服务器容量得到保护。

## 有限验证与交付

同一组核心用例覆盖普通/临时入口：首次估算、实测校准、编辑/重试、切模型、当前与历史图片混合、原生与解析、自动压缩开关、边界值和超限。断言发往上游的内容及拒绝时未调用上游，避免只检查文案。补充一轮工具续问限额验证。界面使用现有组件做浅色、深色和窄屏实际预览；不重复扩大测试或在讨论阶段打镜像。
